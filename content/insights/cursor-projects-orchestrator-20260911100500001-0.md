TL;DR：
> Cursor 发布 Projects（beta）：一个不写代码的"协调者智能体"负责拆解与调度，数千个子智能体并行执行，承接功能开发、代码迁移和持续性维护这类大型工程。智能体工具的竞争焦点正在从"单个模型多会写"转向"编排层会不会管"。

### 架构信号：协调者与工人正式分层

Projects 最值得注意的设计约束是：**协调者本身不写代码**。它只做拆解、分配、进度与质量的管理，具体的编码由数千个子智能体并行完成。这个分工把"规划判断力"与"代码生产力"拆成了两个独立维度——前者依赖强模型的推理能力，后者可以大规模并行堆量。这和制造业把"总工程师"与"流水线"分开是同构的：管理的杠杆率第一次高于生产的杠杆率。

### 适用边界：官方给出了自我定位

按官方介绍，Projects 面向功能开发、迁移和持续性维护等大型工作，并披露了三项核心能力与内部使用数据，供用户判断适配的任务规模。这个定位很诚实：数千个子智能体的并行编排适合目标明确、可拆分、可验证的大体量工作（如版本迁移、批量重构），而不适合需要连续设计思路的探索性开发。工具选型的关键是分清"并行可拆"与"串行思考"这两类任务。

### 展望

与本周 Shopify 迁回原生、OpenAI 开放 Agents API 的消息连起来看，智能体编程的产业分层正在成型：模型层拼推理、编排层拼调度规模、验证层拼质量门禁。Cursor 用 Projects 押注编排层。下一个分水岭是**验证成本**——当写代码近乎免费，"如何确认数千个子智能体没写坏"将成为新的瓶颈与新的生意。
