## 0. 设计命题

> **把这条流水线造成一台可重放的确定性机器；把"判断"压缩到两个地方——一个配置文件，和一个人。**

推论三条（这是红线，后面所有决策都由它们推导）：

| # | 红线 | 反例（现状） |
|---|---|---|
| **R1** | **单一写入者**：整条链路只有一个主体有权写入 `main` | 3 个 n8n 工作流 + ZCode 会话并发写同一棵工作树 |
| **R2** | **判断与动作分离**：模型只产出"内容"，脚本只产出"动作" | 会话既判断又定稿又 commit 又 push |
| **R3** | **可重放**：任一阶段 = `输入目录 → 输出目录 + 决策留痕`，可离线重跑 | 决策发生在会话里，事后无法回答"为什么选了它" |

**为什么"可重放"是第一条工程原则而不是"高可用"**：37 天停更不是一个可用性问题，是一个**可观测性问题**——系统一直在跑，失败 30–50%，而没人能看见。可重放意味着任何一天的产出都能被完整重建和复盘，这比"永不宕机"对内容产品重要得多。

**经济性上的核心判断**：内容工厂的稀缺资源不是模型，是编辑判断。所以系统的目标不是"尽可能多产"，而是**每条产出的边际成本趋近于零、且产量可控**。现状把 9,369 条 RSS 各写一篇全文，而日报只用 5 篇——**漏斗方向错了**。本文的第一条经济学改动就是把漏斗倒过来。

## 1. 先纠正需求本身

你给的链路是：

```
发现选题 → 确认写作 → 查找相关素材 → ai生成 → 自动发布
        → 选取每日最重要的5条 → 创作日报 → 自动发布
```

这条链路有**两处次序问题**，值得在设计前改掉：

| 原链路 | 修正 | 理由 |
|---|---|---|
| 「确认写作」在「查找素材」**之前** | **素材可得性前置到选题阶段** | 有些题目很好看，但没有可核实的一手源。先确认"能写"再确认"要写"，否则确认完的题会在写作阶段变成编造。证据充分度应该是**打分的输入之一**，不是写作的前置步骤。 |
| 出现**两个**「自动发布」 | 合成**一条发布通道** | 日报不是另一条产线，它是另一种"稿件类型"。两条发布路径 = 两倍事故面 + 两套凭据。现状的教训是"改了一处没生效"，根源就是同一件事有多个实现。 |

修正后的链路（**这是本设计的主干**）：

```
① 采集        Source 落地（原始信源条目）
② 归并        Source → Event（同一件事的多条来源合并为一个事件）
③ 评分        Event 打分（含"证据可得性"一维）
④ 排产        配额分流：早报 / 日报 / 洞察
⑤ 取证        抓原文 → 证据包（在制品，不进公开仓库）
⑥ 成稿        模型写作（受风格规范与结构五型约束）
⑦ 门禁        机器可测检查（可否决）+ 分级（T0/T1/T2）
⑧ 发布        唯一通道：CI 提交 → 托管平台构建
⑨ 编排        日报 = 当日 Event 排序 + 主编综述（不是重新写作）
```

## 2. 数据模型：Source → Event → Story

**这是本设计里最重要的一个建模决定。**

原始系统的病根不在提示词、不在封装形式，而在**缺少 `Event` 这个实体**：它把"一条 RSS 条目"当作"一篇文章"的单位。于是同一件事被 5 家媒体报道，就产生 5 篇结构雷同的文章——这既是额度烧穿的直接原因，也是"规模化生成"政策风险最典型的样子（只有 `guid` 判重，无语义去重）。

正确的抽象是**三层**：

| 实体 | 单位 | 关键字段 | 生命周期 |
|---|---|---|---|
| **Source** | 一条信源条目 | `url` `title` `summary` `published_at` `fetched_at` `fingerprint` `tier`(一手/媒体/聚合) | 天级（当天有效，过期即可丢） |
| **Event** | 一件"事" | `event_id` `sources[]` `cluster_key` `score{novelty,impact,clarity,depth,evidence}` `verdict` `reason` | 天级 |
| **Story** | 一篇稿件 | `slug` `event_id` `sources[]` `type`(insight/morning/daily) `tier`(T0/T1/T2) `status` `evidence_hash` | 持久（进 `content/`） |

**为什么 `Event` 是必需的**：它把三个问题一次性解决——
1. **去重**从字符串匹配升级为"归属同一事件"；
2. **日报的 5 条**天然来自 5 个不同的 `Event`（保证"5 条是 5 件事"）；
3. **内链**是免费的：同一 `Event` 的 Source 互为引用，读者看到的是"一件事的多方信源"而不是 5 篇重复稿。

**Story 状态机**（`status` 是 frontmatter 字段，不是目录名）：

```
candidate ──score──> scored ──select──> selected ──evidence──> evidenced
                        │                                        │
                        └──> dropped                             ├──draft──> drafted
                                                                  │
                                              passed ◄──gate──────┘
                                                │        │
                                        ┌───────┘        └──> quarantined（留档待人工）
                                        │
                              (T0/T1) ──┴── (T2) ──> awaiting_review ──> approved
                                        │                                     │
                                        └────────────> published ◄───────────┘
```

`quarantined` 是刻意保留的终局之一：**被门禁拒掉的稿子不删除**，因为"为什么被拒"是改进提示词的唯一燃料。

## 3. 架构：五层 + 一条凭据边界

架构的全部内容可以用一句话概括：**L0–L2 产生内容，L3 独占发布权，L4 只观察**。

（配图见对话中的架构图）

| 层 | 职责 | 运行位置 | 凭据 | 挂掉的后果 |
|---|---|---|---|---|
| **L0 采集** | 拉信源 → 写 inbox | GitHub Actions；国内源由 NAS 代取 | 无发布凭据 | 当天候选变少（可降级） |
| **L1 判断** | 归并 / 评分 / 排产 | Actions（纯 CPU + LLM 调用） | 仅 LLM key | 落回模板轨（T0 仍能出） |
| **L2 生成** | 取证 / 成稿 / 门禁 | Actions | 仅 LLM key | 当天不产深度稿，早报仍在 |
| **L3 发布** | 构建 + 提交 + 部署 | Actions（**唯一持有发布凭据**） | GitHub bot + 托管平台 | 停机（因此 L4 必须能发现） |
| **L4 观察** | 心跳 / 费用 / 失败聚合 | 外部 heartbeat 服务 + `state/runs/` | 无 | 告警失效（因此用第三方） |

**凭据边界是这张图的重点**：L0/L1/L2 全都可以持有 LLM key（它只能花钱，不能改站），只有 L3 持有写权限。这样"某个环节被污染"的最大损失被限制在"多花点钱"，而不是"站点被写坏"。

**NAS 在架构里的位置**：它不是一层，它是 **L0 的国内出口 + 证据/媒体的归档仓库**（见 §12）。

## 4. 目录与状态：什么进 git，什么不进

这是最容易做错的地方。现状把 `public/`（51,940 个文件）和 6,420 张图都放进了 git，于是构建 5 分钟、`index.lock` 事故、仓库膨胀全来了。

**三分法**：

| 载体 | 放什么 | 为什么 |
|---|---|---|
| **git（commit）** | `content/`（已发布）、`pipeline/`（在制品）、`config/`、`prompts/`、`src/`、`.github/`、`state/scores/YYYY-MM.jsonl.gz`（月轮转）、`state/runs/*.json` | 需要审计、需要 diff、需要回滚的东西 |
| **Action artifact（7 天）** | 原始 inbox、证据包全文、构建日志 | 体积大 / 版权敏感 / 只需短期回溯 |
| **Actions cache（跨 run）** | 信源 ETag、已发布索引、LLM 前缀缓存指纹 | 性能优化，丢了只是慢一点 |

目录骨架：

```
neican/
├─ content/                 # 已发布。唯一持久内容资产，append-only
│   ├─ insights/<slug>.md
│   ├─ morning/<YYYY-MM-DD>.md
│   └─ daily/<YYYY-MM-DD>.md
├─ pipeline/<slug>/         # 在制品（有状态）
│   ├─ story.yaml           # status / event_id / tier / 配额
│   └─ refs.json            # 证据包哈希 + 短引用（不含原文全文）
├─ state/
│   ├─ scores/2026-09.jsonl.gz   # 条目级打分（月轮转，学习闭环的燃料）
│   ├─ decisions/2026-09.jsonl   # 选/弃留痕（含理由）
│   ├─ published-index.txt       # 派生，可从 content/ 重建
│   └─ runs/2026-09-11.json      # 每日运行摘要
├─ config/                  # ★ 判断的载体（人读人改）
│   ├─ sources.yaml         # 信源清单 + 分级
│   ├─ scoring.yaml         # 权重 / 阈值 / 配额 / 分类闸标准
│   ├─ models.yaml          # 阶段→模型 + 单价（成本核算用）
│   └─ gates.yaml           # 门禁阈值（可读性 / 引用完整性 / 图片来源）
├─ prompts/                 # 版本化提示词（无密钥）
├─ src/                     # 确定性代码，按阶段分目录
│   ├─ fetch/ score/ select/ evidence/ draft/ verify/ publish/ digest/ report/
│   └─ lib/                 # llm 客户端（含缓存/限流/重试）、指纹、schema
├─ site/                    # Hugo 源码 + 主题（无 public/、无 6k 图片）
├─ tests/                   # 门禁自测（含"提示词不得含密钥"用例）
└─ .github/workflows/
```

**关键设计：状态的"当日幂等 + 派生索引"**。
去重不需要无限累积的永久记忆——它只需要两件事：① **当天幂等**（同一条目当天只评一次，用 `source_url` 哈希）；② **已发布集**（`published-index.txt`，本身就是 `content/` 的**纯函数**，可随时重建，因此永不腐坏）。被拒绝的条目三天后再出现？重新花 1 分钱评一次，比维护无限增长的 rejection 库便宜得多。**这是"状态不腐坏"的关键：能派生的绝不存储。**

## 5. 编排：GitHub Actions 作唯一调度器

只用 Actions，理由：公开仓库免费不限时长、密钥管理原生、artifact/cache 原生、**与 Issue/PR 同一平台**（审批台不用另建，见 §10）、workflow 是版本化文件（可直接 diff 与回滚）。

**Workflows（6 个）**：

| 文件 | 触发 | 职责 |
|---|---|---|
| `pipeline.yml` | cron `0,30 21-23,0-13 * * *`（北京 05:00–21:00 每 30 分） | L0→L1：采集 / 归并 / 评分 / 排产 |
| `daily.yml` | cron `0 23 * * *`（北京 07:00）+ `0 11 * * *`（北京 19:00） | 早报与日报的编排 |
| `publish.yml` | `workflow_call` + `workflow_dispatch` | L2→L3：取证 / 成稿 / 门禁 / 提交 / 部署 |
| `editor.yml` | `issue_comment` / `issues.edited` | 主编台命令（见 §10） |
| `weekly-review.yml` | cron `0 1 * * 1`（北京周一 09:00） | 学习闭环：权重重标定 PR |
| `self-check.yml` | `pull_request` | 门禁逻辑的自测 + 密钥扫描 |

**三个必踩的坑（已验证，直接写进设计）**：

1. **Actions cron 只认 UTC，且只跑默认分支。** 早报北京 07:00 = UTC 前一日 23:00。写成 `0 7 * * *` 会在 15:00 触发，而且从文件表面看不出来。
2. **scheduled workflow 会被延迟**（高负载时数分钟到数十分钟）。"早报 7:30 必须准点"不能靠 Actions cron 保证 → **时间敏感的两个 run 由外部 cron（cron-job.org / Cloudflare Worker）经 `workflow_dispatch` 触发**。这是把"准点"从平台行为变成我们可控的行为。
3. **必须设 `concurrency`**，否则同一条流水线的两次触发会互相踩：

```yaml
concurrency:
  group: pipeline-${{ github.ref }}
  cancel-in-progress: false
```

**成本优化附赠**：DeepSeek 的峰谷定价分界是北京时间 09:00–12:00 与 14:00–18:00。早报（07:00）与日报（19:00）**天然落在低谷时段**，单价直接减半。设计上再补一条规则：**非紧急的批量任务（存量重算、归档）排到 18:00 之后或周末**（周末全天低谷）。

## 6. 模型规划

### 6.1 第一原则：可移植性 > 缓存命中 > 价格 > 峰值能力

选模型的第一条不是质量也不是价格，而是**"它在两地都可达吗"**（GitHub runner 在海外，NAS 在国内）。如果选了国内不可达的供应商，"生成在哪跑"就被锁死，架构自由度消失。**先让供应商选择不决定部署拓扑，再谈其它。**

第二条是**缓存命中价**，因为 Agent 类工作流是"长输入 + 前缀高度重复"的消耗模式——同一个 system prompt 和评分量表一天要发上千次。这一项的差价是 8–31 倍，远超峰谷的 2 倍。

### 6.2 阶段分配（价格已核准至 2026-09）

| 阶段 | 首选 | 单价 | 为什么 |
|---|---|---|---|
| **S1 分类闸**（~1,500 条/天） | GLM-4.7-Flash | **免费**（200K ctx，30 并发上限） | 唯一"永久免费"的一档，且原生支持 JSON 输出。**必须配限流器**（30 并发是硬约束） |
| **S2 打分**（~300 条/天） | 同上，或 DeepSeek-V4-Flash | 免费 / ¥1.5·¥4.5 每百万（闲） | 只需产出子分与理由，Flash 档足够 |
| **S3 素材抽取** | DeepSeek-V4-Flash | ¥1.5 输入（缓存命中 **¥0.05**）· ¥4.5 输出 | 长输入场景，命中价决定成本 |
| **L2 深度稿**（2–3 篇/天） | **DeepSeek-V4-Pro** | ¥4.5·¥13.5（闲） | 中文科技写作的第一梯队；每天只写 2–3 篇，贵得起 |
| **L2 早报/日报综述** | DeepSeek-V4-Pro 或 GLM-5.3 旗舰 | 同上 / ≈¥10·¥31 | 1–2 次/天，成本可忽略 → **要最强的** |
| **审校/事实核对** | **与写作不同家的 Flash**（GLM 写 → Qwen 审） | ¥0.8·¥2.7 | **不同模型的错误相关性低**，这是交叉验证的全部意义 |
| **图片理解** | deepseek-v4-flash-vision-exp | 与 flash 同价 | 一个 key 覆盖文本 + 视觉 |
| **Agent（Codex 类）** | DeepSeek-V4-Flash | 同 flash | 官方支持 Responses API 并可接入 Codex |

### 6.3 三条成本设计规则

1. **固定前缀**：system + few-shot + 评分量表放在 prompt 最前，逐字不变 → 命中缓存。
2. **批量请求**：一次打分 20 条而不是 20 次请求。前端只发一次，N 条共享同一份前缀。
3. **不用模型做算术**：加权公式在 `config/scoring.yaml`，模型只出子分。省 token，且让权重可被人工调参（这是学习闭环的落点）。

### 6.4 成本预算（基准：候选 1,500/天，成稿 3 篇洞察 + 早报 + 日报）

| 项 | 日成本 |
|---|---|
| 分类闸（GLM-4.7-Flash） | ¥0 |
| 打分（免费档） | ¥0 |
| 素材抽取 | ≈¥0.05 |
| 深度稿 3 篇（V4-Pro 闲时） | ≈¥0.25 |
| 早报 + 日报综述 | ≈¥0.30 |
| 审校（Qwen3.8-Flash） | ≈¥0.03 |
| 视觉理解 | ≈¥0.02 |
| **合计** | **≈¥0.65/天 ≈ ¥20/月** |

若打分也换成付费 Flash，上限约 **¥2/天（¥60/月）**。加 Actions（公开仓库免费）、Tailscale（免费档）、托管（免费档）——**整站月度现金成本 ≈ ¥20–60**。

对照：原系统的成本不是"模型太贵"，是**漏斗方向错**（9,369 篇全文 + 逐篇搜索 + 逐条搜图，而日报只用 5 篇）。**这个月成本数字本身就是设计正确性的证据。**

## 7. 选题机制（继承原始意图，落到代码）

四段式，与 `SPEC-selection-and-style-2026-09-11.md` 一致：

| 段 | 做什么 | 成本 | 落点 |
|---|---|---|---|
| **S0 规则预筛** | 时效窗 / 域名分级 / 指纹去重 / 语言 | ¥0 | `src/select/` |
| **S1 分类闸** | 恢复原始的 7 条 include/exclude 判断标准（"AI 内参是什么"的定义），并新增一问：**"这条对中文读者有什么用"** | 免费模型 | `prompts/01-classify.md` |
| **S2 打分** | 五维子分：novelty / impact / clarity / depth / **evidence**（新增）。模型只出分与理由 | 免费或极低价 | `prompts/02-score.md` + `config/scoring.yaml` |
| **S3 排产** | 加权排序 → 配额分流 → 落选留痕 | ¥0 | `src/select/` |

**为什么新增 `evidence` 证据充分度（权重 0.20）**：原始设计没有"能不能核到事实"这一维，这正是后来 9,369 篇只能靠聚合摘要成文的结构性原因。有了它，**"好看但核不动"的题目会在选题阶段就被淘汰，而不是在写作阶段变成编造**。

**配额**：早报 8–10 条 / 日报 1 期（5 条）/ T1 洞察 ≤3 / T2 洞察 ≤2。落选全部写 `state/decisions/`。

**闭环**（原始设计漏掉、现状也没有的一环）：

```
打分 → 发布 → analytics（按维度分组看落地页会话数）→ 每 2 周重标定权重 → config/scoring.yaml 的 PR
```

没有这一步，"选题质量"就还是审美。有了它，**它变成一个可回归的配置项**，并且每次调整都是一次可审、可回滚的提交（由每周的 agent 会话产出，见 §11）。

## 8. 素材与证据包

"查找相关素材"在这一行里最容易被做成黑箱。工程化的定义是**证据包（evidence pack）**：

```
pipeline/<slug>/
├─ story.yaml
├─ refs.json          # 每个引用 → {source_url, fetched_at, sha256, quote(短引用)}
└─ (原文全文不落仓库，只落当次 run 的 artifact)
```

**三条硬规则**：

1. **成稿只能引用证据包内的内容**。事实核对因此可机器化：稿中的引号内容必须能在证据包里找到匹配（允许标点与省略号差异）。这一条直接消灭"编造数字引语"。
2. **原文全文不进公开仓库**。抓取的第三方全文若提交进公开库，等于再分发，是版权风险（HANDOVER 只考虑了图片，漏了这一项）。设计上：全文只在当次 run 的 artifact 里（7 天），run 结束后归档到 NAS；仓库里只留**短引用 + 哈希 + 抓取时间**——既保住了可审计性，又不构成再分发。
3. **图片三来源，默认无图**：① 来源原文的 `og:image`（附来源标注）；② 官方新闻稿配图；③ **程序生成的封面卡片**（标题 + 主题色 + 站名，零版权风险）。**不使用搜索引擎搜图**（现状的做法：版权风险 + 仓库膨胀 6,420 张）。

## 9. 生成与门禁

风格约束拆成三层（与 SPEC 一致），关键是第二层**可以否决发布**：

| 层 | 内容 | 执行者 |
|---|---|---|
| ① 生成指令 | 深度解释型科技报道 + **结构五型 A–E + 决策指南**（突发/深度/人物公司/对比/教程）；每段一个观点；关键数据独立成段 | LLM（`prompts/03-draft.md`） |
| ② **机器可测门禁** | 段落 >150 字 ✗、句子 >60 字 ✗、`###` 小标题 >3 个 ✗、套话 >2 处 ✗、无 TL;DR ✗、正文字数 800–1800、引用完整性、图片来源合法、frontmatter schema、`main_topics` 闭集、占位符正则 | `src/verify/`（纯代码，**可否决**） |
| ③ 评审清单 | 观点是否站得住、标题是否有信息量、是否值得发 | 人 / agent |

②层的阈值来自**存量 400 篇实测基线**（超标比例：小标题 73.0%、长段 51.2%、长句 75.2%）——注意**长度不是问题（中位数 1,252 字合格），粒度和结构才是**。这三条完全可机器化，所以"可读性"从审美变成了可执行的约束。

**`main_topics` 闭集**这一条顺带治掉存量的 634 个分类碎片：分类不再由模型自由发挥，只能从 `config/` 的枚举里选。

## 10. 人的位置：Issue 主编台 + 三条产线

**不建前端。** GitHub Issue 天然提供：清单、勾选、评论、时间戳、移动端 App、全文检索、可追溯——而我们要的恰好就是这些。**审批台 = 一个 Issue，命令 = 一条评论。**

```
每天 08:00  CI 开一个 Issue：《📋 9/11 选题 12 条待确认》
            body 是可勾选清单（标题 / 来源 / 五维分 / 一句话理由 / 建议层）
主编动作      ① 手机勾选后 merge？不必——直接评论：/write 3,7,9
             ② /drop 5,11  /hold 2  /write <任意 URL>（插单）
             ③ 不评论 → 超时按默认策略走（T0/T1 自动，T2 顺延到明日）
editor.yml   issue_comment → 解析 → 推进状态机 → 触发 publish.yml
```

**三条产线，风险分层**（这是"自动化"与"质量"的和解点）：

| 产线 | 内容 | 闸 | 政策风险 |
|---|---|---|---|
| **早报**（T0） | 8–10 条聚合：标题 + 摘要 + 署名 + 原文链接，**零创作** | 无人自动发 | 最低（聚合 + 链接，来源可核） |
| **日报**（T1） | 当日 5 个最强 Event + 主编综述（**输入只有结构化摘要，没有全文可抄——强制它做综合而非复述**） | CI 自动发，事后抽检 | 低（事实层来自一手源） |
| **洞察**（T1/T2） | 深度解释稿 | T1 自动发；**T2（含数字/观点/争议/独家判断）走 Issue 待确认** | 集中在 T2，可控 |

**超时默认策略很重要**：如果主编三天不看 Issue，T0 照常出、T1 照常出、T2 顺延。**站点的更新频率不依赖任何人的在线状态**——这是对"PC 关机 = 停刊"的结构性回答。

## 11. Agent 的位置

**原则：Agent 在链路旁，不在链路里。**

理由不是"agent 不行"，而是**链路需要的性质（确定性、可重放、便宜、可并发）与 agent 的性质（会话式、非线性、贵）在数学上不兼容**。把 agent 放进 cron，等于把不确定性放到唯一有发布权的通道上。

| 场景 | 谁 | 产出形态 |
|---|---|---|
| 采集 / 归并 / 打分 / 排产 / 成稿 / 门禁 / 发布 | 脚本 + CI | commit |
| T2 稿件的判断与核实 | 主编（人）；agent 可辅助开原文 | Issue 评论 / PR review |
| **每周选型复盘**（权重重标定） | WorkBuddy 会话，每周一次 | `config/scoring.yaml` 的 **PR** |
| **信源扩充 / 新源试探** | agent 自由探索 | `config/sources.yaml` 的 **PR** |
| **管线代码改动** | Codex / ZCode（worktree + 分支 + PR） | **PR** |
| **事故诊断** | agent（正是本次做的工作） | 报告 + PR |

**统一约束：agent 的一切产出都是 PR 或 Issue 评论，没有直接发布权。** 于是 agent 崩了、说错话、烧光额度，都不会污染站点——最坏情况是一个没人 merge 的 PR。这条约束让"要不要用 agent、用哪个 agent"从架构问题降级为工具偏好问题。

## 12. NAS 的分工

两台机器各有天职，**都不要做生产编排**：

| 机器 | 角色 | 具体做什么 | 为什么是它 |
|---|---|---|---|
| **群晖 192.168.50.247** | **入口（国内出口）** | 自建 RSSHub（已在 `:1300`）适配无官方 RSS 的源；一个 ~50 行 Python 把条目写成 inbox | 它已经在跑 RSSHub。**国内源在海外 runner 上是否可达是未验证风险**——把"取数"放在国内是唯一稳妥解 |
| **TrueNAS 192.168.50.224** | **仓库（归档层）** | 证据包全文、原始快照、图片库、备份（ZFS 快照/校验） | 存储是它的天职；且这批数据**体积大、版权敏感、不该进公开仓库** |

**连接方式：Tailscale（已有）。CI 用 ephemeral key 加入 tailnet 去拉 NAS，而不是 NAS 推 GitHub。**

- 方向很关键：**推**意味着 NAS 要持有 GitHub 凭据（又多一个泄露面）；**拉**意味着 NAS 零凭据、零公网暴露，唯一的秘密在 GitHub 侧的 Tailscale OAuth 客户端。
- 顺带消除一处歧义：**停掉 `224:30109` 的实验 n8n 容器**。HANDOVER 自己写了"两台机器各有一个 n8n 实例，容易混淆"——而"容易混淆"在事故里的代价很实。

**群晖的资源提醒**：8GB 内存已跑 n8n + RSSHub + Dify 全套（且曾因常驻 Hugo 容器吃 94% CPU）。建议**停掉 Dify**——HANDOVER 已否决它做生产层，留着只是占内存。

## 13. 托管与可访问性（面向中国读者）

这一节在原始方案里完全缺失，但对一个中文站点是硬约束：

1. **`.ai` 域名无法在国内备案** → 不可能用国内 CDN/OSS，只能境外托管。现状 Vercel 在部分国内 ISP 上不稳定；**Cloudflare Pages 通常更稳**（anycast + 免费不限带宽），值得 A/B 实测后切换。
2. **GA4 的 `gtag.js` 在国内被墙**：每次访问都挂一个超时请求，直接拖慢首屏。建议换 **Cloudflare Web Analytics**（无 cookie、可达）或**自建 Umami 挂在 NAS**（顺带给 NAS 一个正当用途）。
3. **图片出仓**：6,420 张图进 git 是构建 5 分钟的主因。改为 Cloudflare R2（免费额度 10GB、出网免费）+ 自定义域，仓库只留站点图标。**预期构建降到 1 分钟以内**。
4. **模板成本**：`.Site.RegularPages.Related` 会扫描全站。显式声明 `[related]` 索引（`tags` + `main_topics`）并限制条数——这个是 O(全站) → O(索引) 的差别。
5. **`public/` 必须移出仓库**（这是本文与既有方案唯一的强制项）：产物由托管平台构建，仓库只存源码。

## 14. 失败设计

这一节是本次 37 天事故的直接产物。**"在能观测之前做自动化，等于自动化一个黑箱。"**

| 机制 | 形态 | 治什么 |
|---|---|---|
| **心跳倒挂** | 每次成功发布 → ping 外部 heartbeat 端点；**无心跳即告警**。检查方在第三方，无需自建 | 轮询会在"检查器自己死掉"时静默失效；心跳不会 |
| **运行摘要** | 每次 run 写 `state/runs/YYYY-MM-DD.json`：各阶段条数、耗时、token、成本、失败原因 | "今天为什么只有 2 篇"应当能被文件回答 |
| **分级降级** | LLM 全挂 → 模板轨：早报仍能出（标题 + 来源 + 链接，无 LLM 也是合法产品） | 单一供应商断供导致全站冻结 37 天 |
| **熔断** | 连续 3 次 run 失败 → 自动 `gh workflow disable` + 告警 | 失败 30–50% 却被当成"在跑" |
| **成本闸** | 单日 LLM 花费 > 阈值 → 停生成 + 告警（现在阈值可以设得很宽松，¥10/天足够） | 额度静默烧穿 |
| **密钥扫描** | `self-check.yml` 在 PR 上扫 `ghp_` / `sk-` / `tvly-` / 私钥 | 明文 PAT 硬编码在模板里并被渲染进线上页面（本次实测的真实事故） |

**为什么心跳优于看门狗**：n8n 容器是 `restart: "no"`——宿主重启后它不会自己回来。**一个需要被观测的进程，不能承担观测职责。**

## 15. 落地路线（每步都有验收标准）

| 相位 | 内容 | 验收标准 | 可逆性 |
|---|---|---|---|
| **P0 凭据** | 轮换 PAT / Tavily / CSE；PAT 换 fine-grained；全部进 Secrets；清掉模板里的密码行 | 线上页面 `grep` 不到任何密钥；`git log -S'ghp_'` 无新增 | 不可逆但必须 |
| **P1 出仓** | `public/` 移出版本控制；图片迁 R2；`[related]` 索引显式化 | 构建 < 2 分钟；仓库文件数降一个数量级；线上无回归 | 可逆（git revert） |
| **P2 骨架轨** | L0 采集 + L1 归并/评分 + 早报模板轨 + 心跳。**不接 LLM 也能出早报** | **PC 关机 48 小时，站点照常更新** | 可逆 |
| **P3 判断轨** | 分类闸 + 五维打分 + 配额 + `decisions/` 留痕 + 学习闭环 | 每次选题都能给出"为什么是它"的理由链 | 可逆 |
| **P4 生成轨** | 证据包 + 结构五型 + 机器门禁 + T0/T1/T2 分流 | 门禁拦下的稿件有记录；引用完整性可机器校验 | 可逆 |
| **P5 主编与 agent** | Issue 主编台 + 每周复盘 + agent 只出 PR | 一周不碰 Issue，站点更新不中断 | 可逆 |
| **P6 存量治理** | 634 个 `main_topics` 收敛、4,904 处占位符清理、931 张坏配图修复 | 门禁在存量全量上跑通为 0 违规 | 可逆（逐批） |

**顺序不可交换的只有两条**：
- **P0 必须最先**：在能观测之前做自动化，等于自动化一个黑箱。
- **P1 必须早于 P2/P3**：否则自动化只会更快地制造大 diff 和锁冲突。

## 16. 明确不做

1. **不把 agent 放进 cron。** 它做判断，不做轮询。
2. **不让任何组件直接 push `main`**，除 L3。
3. **不做"每 30 分钟必须产出"的 SLA。** 没有观测数据支撑任何频率结论。
4. **不重建节点式编排（n8n 形态），也不重建会话式编排（当前形态）**——两者是同一个错误的两面：把确定性的事交给了不确定的执行者。
5. **不在公开仓库放第三方全文**（版权），也不放图片大件。
6. **不用搜索引擎搜图**。
7. **不让分类由模型自由发挥**（闭集），**不让模型做算术**（权重进配置）。
8. **不追求产量**。产量是配额的函数，不是目标。
