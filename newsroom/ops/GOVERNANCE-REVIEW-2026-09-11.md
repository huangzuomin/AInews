## 0. 一句话结论

**"生产线跑起来了"是真的；"内容能按时到读者手里"还不是。**

一条链被切成四段，通了三段：采集→排产、编排落盘、调度 都已实测通过；
断的是 **NAS→GitHub（凭据）**，而 **Vercel→CF→读者** 这一段因边缘缓存严重滞后。
更麻烦的是：**三条红线里，"单一写入者"仍被旧产线违约，"判断与动作分离"只剩形式。**

## 1. 三条红线对照

### 1.1 单一写入者 —— ❌ 仍违反（有实证）

`git log -20` 显示旧产线的自动化提交**确实在写 GitHub main**：

```
66c0760cd2  09-11 07:04  流水班 10:00：洞察《Cursor Projects：协调者智能体指挥数千子智能体》
82e2e9861a  09-11 06:36  早报 2026-09-11（10条）+ 补推积压：Agents API、蒸馏攻击两篇洞察
eb6a4e7423  09-11 05:10  流水班 05:00：洞察《Anthropic 披露蒸馏攻击》+ 补推积压的 Agents API 一篇
9abcfa8f3e  09-11 04:34  流水班 04:30：洞察《OpenAI Agents API 公测版》
```

署名统一为 `huangzuomin <h.zuomin@gmail.com>`，消息模板为「流水班 HH:MM：洞察《…》」。
**最后一条 07:04，之后就停了** —— 与本轮观察到的"站点 06:35 后无产出"一致。

**风险**：NAS 一旦拿到 push 凭据，两条链会同时写 main → 非快进冲突或相互覆盖。
`emit.sh` 的降级路径会把它记成 `pushed=0`（不丢数据），但会形成
**"永远推不上去、且看起来像没凭据"的静默僵局**。

**因此动作顺序不可颠倒**：

```
停群晖 n8n  →  确认 main 不再出现外部提交  →  再给 NAS 凭据
```

#### 附带发现：提交身份不可区分

NAS 上 `git config user.name = neican-bot`，而 `emit.sh` 提交时也是
`-c user.name='neican-bot'` —— **人工/agent 的改动与流水线产出在历史里长得一模一样**。
审计时无法回答"这个提交是谁产生的"。建议：流水线用 `neican-bot`，
人工/agent 用另一身份（或至少加 `Produced-By:` trailer）。

### 1.2 判断与动作分离 —— ⚠️ 形式成立、实质未接通

设计共识是"NAS 只 commit，**CI 保留校验+部署**，发布权只归 CI"。实测：

| 检查 | 实测值 | 含义 |
|---|---|---|
| `GATES_ENFORCE` | `false` | 门禁 **warn-only**，不拦截 |
| `DEPLOY_TARGET` | **未配置** | CI 的 deploy job 恒为 `skipped` |
| Vercel 部署 | push 后自动产生 **Production deployment** | ← **关键** |

第三条推翻了一条隐含假设：**发布路径不经过 CI**。Vercel 用 GitHub 集成自行构建并部署，
CI 的门禁（含唯一阻断性的 G3-b）**只阻断 CI 自己的 job，不阻断 Vercel 的部署**。

> 换句话说：现在**发布权在 Vercel，不在 CI**。门禁被挂在了一条不在发布路径上的链上 ——
> 这在治理上叫"装饰性门禁"：它每天变绿，但它拦不住任何东西。

**这需要一次架构决策**，两条路：

1. **门禁前移到 NAS（写入侧）**：`emit.sh` 在 commit 前跑 `validate.py`，
   不通过就不提交。发布路径 = push，门禁天然在链上。
2. **让 Vercel 只部署被验证过的提交**：CI 校验通过后打 tag / 置 commit status，
   Vercel 的 Git 集成改为只对特定条件部署（或直接改用 Deploy Hook 由 CI 触发）。

方案 2 更符合"发布权只归 CI"，但要改 Vercel 项目设置；方案 1 立刻可做、零外部依赖。
**建议先做 1（立刻有效），再评估 2。**

### 1.3 可重放 —— ✅ 基本成立，有一处真缺口

已成立的：

- `raw/<day>/` 原文**原样落盘**（gzip，可重放凭证）
- `state/` 全留痕：`events-*.jsonl` / `scored-*.jsonl` / `classified-*.jsonl` /
  `rejected-*.jsonl` / `decisions/` / `plan-*.json`，**落选的也留**
- 全过程无隐藏状态，`pipeline.sh --from <stage>` 可从任意阶段重跑

**缺口（实测）**：`plan-2026-09-11.json` 的顶层字段只有
`by_id / counts / daily / day / generated_at / insights / morning` ——
**没有记录当时的 config 指纹，也没有 repo HEAD**。

后果：改了 `scoring.yaml` / `classify.yaml` / `sources.yaml` 之后重跑同一天，
会得到**不同结果**，而且**无法证明当时用的是哪一版**。
"可重放"于是只能"大概能"，不能"可证"。

**处置**：`plan-*.json` 与运行记录里增加 `config_sha`（4 个 config YAML 的合并哈希）
与 `repo_head`。成本极低，收益是把可重放从"声称"变成"可查"。

**保留策略缺失**：`raw/` 约 3.2 MB/天（≈1.2 GB/年）、`state/` 约 814 KB/天。
目前不痛，但必须**显式定策略**（建议 `raw/` 保留 90 天、`state/` 保留 1 年），
否则会在某天以"磁盘满 → 写入静默失败"的形式爆发。

## 2. 凭据边界

| 项 | 现状 | 判断 |
|---|---|---|
| NAS push 凭据 | **无**（通道已铺：`credential.helper` → 仓库外 600 文件，目录 700） | ✅ 符合"NAS 零凭据"原设计 |
| 旧 PAT `ghp_****Jj8W` | **仍存在** —— `D:/Work/n8n/hugo_sync_workflow.json` 实测扫描命中明文 | ❌ **P0**：一个在版本控制视野外、未被审计、可能仍可写仓库的凭据 |
| 细粒度 token | 未申请 | 需 `Contents: **Read** and write` |
| PC 中转 | `git fetch nas` + `git push origin refs/remotes/nas/main:refs/heads/main` | ✅ 只搬引用，**不碰工作区、不产生提交** |

**为什么强调 Read**：`git fetch` 是读操作。缺读权限时 NAS 永远算不出
`commits_ahead_of_origin`，只能记 `-1`（"未知"）—— 而那**正是判断"发布链断没断"要看的那个数**。
只给 `write` 会得到一个会推、但看不见自己落后多少的 NAS。

## 3. 观测

### 已补齐（本轮）

对外（站点新鲜度）与对内（生产线自产、工作区、磁盘、调度器）两条通道齐了，
且**告警能区分两种病**：

- 「没产出」→ 本地 `rc≠0`
- 「产出了没发布」→ 本地 `rc=0` 但 `已提交未推送`

实测告警体（21:49）：

```
全站        09-11 06:35  15.2h / 14h   ← 超阈
生产线产出   09-11 21:48 daily rc=0，已提交未推送(ahead=-1)  0.0h / 14h
> 本地已产出但未推送 —— 站点停更的直接原因在发布链，不在生产线。
```

### 仍缺

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **告警无投递** | 钉钉 webhook 未配 | 检测存在、结论正确、**无处可去**。当前站点确实停更 15.2h，告警正被 6h 重报窗口抑制 |
| 2 | **对外信号被 CF 缓存污染** | Vercel Production 部署 21:33（`e6704cbf`），而 21:41 抓 `/index.xml` 得到 `cf-cache-status: HIT`、`Age: 10197`（≈18:50 的副本）；22:0x 再看仍是 HIT、`Age: 11152` | watchdog 的"线上最新条目时间"**最多滞后一个 CF 缓存周期**。阈值 14h 因此被拉长，**检测延迟可达 14h + 缓存时长** |

第 2 条是本次的新认识：**P8（CF 缓存）不只是 SEO/GEO 问题，它同时是观测问题**。
一个为了让读者更快看到内容的缓存，正在让"内容坏了没人发现"。

### 3.5 交付物是否真的"可达" —— 本轮新增的一类检查

摸清 CF 缓存的**实际范围**（22:00 实测）：

| 路径 | 状态 | cf-cache-status | Age | 含义 |
|---|---|---|---|---|
| `/index.xml` | 200 | `HIT` | 11,332 | RSS **被缓存**（← watchdog 读的就是它） |
| `/sitemap.xml` | 200 | `HIT` | 11,315 | sitemap 被缓存 |
| `/robots.txt` | 200 | `HIT` | 21,032 | robots 被缓存（≈5.8h 前的副本） |
| `/llms.txt` | **404** | `HIT` | 11,314 | ← **见下** |
| `/newspaper/2026-09-10-09-10-/` | 200 | `DYNAMIC` | 15 | HTML 页面**不被缓存**（近乎实时） |
| `/morningnews/2026-09-11-…/` | 200 | `EXPIRED` | 0 | 同上 |
| `/` | 200 | `DYNAMIC` | 0 | 同上 |

于是 P8 的严重性需要**精确修订**：CF 缓存的是**非 HTML 资源**（xml / txt），
HTML 页面是实时的。所以它对"读者的阅读体验"影响有限，
但**对 AI 爬虫与观测影响很大** —— `llms.txt` / `sitemap.xml` / `robots.txt` 正是
GEO 的入口文件，而 `index.xml` 正是看门狗的信号源。

**然后发现了更麻烦的一件事**：`/llms.txt` 返回 **404 且被 CF 缓存**（`Age: 11314`）。
用绕缓存的方式复验：

```
GET /llms.txt?cb=<ts>   →  200  MISS      ← 源站是好的，内容是真正的 llms.txt
GET /llms.txt           →  404  HIT       ← 边缘层依然是"不存在"
```

**结论：CF 把 404 负缓存了。** `static/llms.txt` 在仓库里（提交 `4a5cd2f443`）、
在源站上（200），但**通过 CDN 拿到的仍是 404**。而 AI 爬虫走的就是 CDN。

> 这意味着 P0.8 的交付物**实际不可达**，且**构建后抽检（G3-b）永远发现不了** ——
> G3-b 检查的是 CI 的构建产物，而问题出在"产物 → 边缘"这一段。

**由此得出一条通用治理要求**：
**凡"构建/部署成功"的判定，都必须补一次「served-state 抽检」**
（对关键路径发一次绕缓存的请求）。本项目已经因为"构建不报错但产物为空"栽过一次
（`_internal/schema.html` 在 Hugo 0.147 被清空 → 全站 JSON-LD 覆盖率为 0），
这次是同一类病的第二个变种：**"产物存在但不被服务"**。
