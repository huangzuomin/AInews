# neican.ai 生产自动化设计

- 日期：2026-09-11
- 配套：`REVIEW-zcode-plan-2026-09-11.md` §5（本文件**替代该节 §5.2 的概述**，把它落到可执行形态）
- 依据：仓库实测（remote、`.github/` 为空、`.gitignore` 仅 `newsroom/`、`vercel.json` 无构建配置、`deploy.py` 71 行 5 跳链路）

---

## 0. 立场

一句话：**能让脚本做的绝不交给会话；只有需要判断的地方才用 agent，而且它输出批注，不输出发布动作。**

现状把 agent 放在**执行器**位置（每 30 分钟拉数据、查重、写稿、QC、部署全在一个会话里）。结果是：不可单测、不可回滚、不可审计、不可复现，且 48 次/天。自动化要解决的不是"让 agent 更勤快"，而是**把它从流水线上摘下来，放到主编的位置**。

---

## 1. 先划边界：什么该自动化

| 判据 | 归属 | 落点 |
|---|---|---|
| 同一输入永远同一输出 | 脚本 / CI | L0 采集、L1 去重、L3 构建发布 |
| 失败可被机器判定 | 自动化 + 硬闸 | L2 schema 校验、门禁、L4 告警 |
| 要判断"哪件事更值得写" | 人 / agent | L5 选题取舍、事实核验、复盘 |

反例（现状）：`RUNBOOK.md` 的班次 SOP 把五类工作打包成"值班班次"，其中四类是可确定性的，却被写成了一个会话的现场发挥。**可确定的部分被会话化，是这个产线的根本病灶**——它同时解释了"改了没生效"和"37 天无人察觉"。

---

## 2. 目标形态：L0–L5

| 层 | 职责 | 实现 | 频率 | 可单测 | 失败可见 |
|---|---|---|---|---|---|
| **L0 采集** | 拉 aihot 精选 + 官方 RSS 兜底 | 单文件 Python，纯标准库 | 每小时 | 是（喂 fixture） | 非零退出 → workflow 失败 → 告警 |
| **L1 去重** | URL 规范化 hash + 标题 3-gram 指纹 | `state/seen.jsonl` | 同上 | 是（纯函数） | 同上 |
| **L2 生成** | 队列 → 模板化 md，frontmatter 强校验 | 双轨：无 LLM / 有 LLM | 同上 | 是（schema 断言） | 校验失败即拒绝并记录原因 |
| **L3 构建发布** | `hugo --minify` → CDN | 云端 CI | push 触发 | — | 构建失败阻断发布 |
| **L4 观测** | 心跳 + dead-man switch + 运行审计 | 一次 HTTP GET / 一个 JSON 产物 | 每 6 小时 | — | 停更 >6h 主动告警 |
| **L5 判断力** | 选题取舍、原文核实、质量批评、周复盘 | **agent，1–2 次/天，产出批注** | 每天 | 否（本就不该） | 批注即产物，可 diff |

agent 从 48 次/天降到 1–2 次/天，token 消耗降约 95%；更重要的是它的输出从**不可追溯的发布动作**变成**可审阅、可 diff 的批注**。

## 3. 八个关键设计决策

### 3.1 调度的单一事实源 = workflow YAML

现状两份文档的排班互相矛盾（`HANDOVER` 06:30 vs `RUNBOOK` 06:40；19:30 vs 19:15；"每 30 分钟" vs "每日 4 班"）。原因不是笔误，是**调度器活在会话状态里**，文件只能事后追认。

目标：cron 表达式只写在一个地方（workflow YAML），RUNBOOK 改为引用它。

> **坑（必踩）**：GitHub Actions 的 cron **只认 UTC**，且只跑默认分支。
> 早报 06:40 CST = **`40 22 * * *`**（UTC 前一日）；日报 19:15 CST = `15 11 * * *`。
> 写 `40 6 * * *` 会变成北京时间 14:40，而且这个错误在文档里看不出来。

### 3.2 去重从"grep 全库"变成状态表

现状 `RUNBOOK` 要求"写稿前在 `content/insights/` + `newspaper/` + `morningnews/` 里 grep 关键词"——每次决策 O(9,376 个文件)，且依赖会话现场执行，不可复现。

目标：`state/seen.jsonl`，每行 `{hash, title_fp, url, first_seen, decided}`。查重变成一次内存查找，可导出、可审计、可回放。

### 3.3 生成轨双模（这是"永不断更"的机制）

| 轨 | 内容 | 依赖 LLM | 边际成本 | 作用 |
|---|---|---|---|---|
| **确定性轨** | 早报 / 日报：结构化字段 → 模板渲染（标题 + 来源 + 一句话事实 + 原文链接） | **否** | 0 | 站点下限，永不失败 |
| **增强轨** | 洞察 / 深度稿：一次 LLM 调用/篇 | 是 | 每天几分钱 | 上限，可失败可降级 |

关键：**增强轨失败（限流/欠费/超时）时降级到确定性轨，站点照常更新。** 现状是"agent 会话没跑 → 当天什么都没发生"。

### 3.4 LLM 供应商抽象（决定这套东西能不能自动化）

三个环境变量：`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`，走 OpenAI 兼容协议。换供应商不改代码。

这条的意义：现在内容生成**骑在 ZCode 订阅上**——订阅不可被 CI 调用，所以"上云"在架构上就被堵死了。把它换成一个 API key（存 GitHub Secrets，不进 `config.json`、不进模板），"边际成本 0"变成"每天几分钱"，换来的是**这条产线第一次可以被自动化**。

> 可达性注意：GitHub runner 在海外，可达 OpenAI / Anthropic / 官方 RSS；从 NAS 走则 OpenAI 不可达（已实测）。**生成放云端还是 NAS，和 key 选哪家要一起定**（见 §9-1）。

### 3.5 生成物必须过 schema 才能入库（一次修掉四类存量病灶）

入库前硬校验，不通过就拒绝并记录原因：

| 校验 | 拒绝条件 | 顺手修掉的存量问题 |
|---|---|---|
| frontmatter 必填 | 缺 title/date/summary/tags/main_topics | — |
| `main_topics` 闭集 | 不在白名单内 | **634 个分类值碎片化**（从源头不再增长） |
| 占位符正则 | 命中 `YYYY` / `{{ }}` / `TODO` | **4,904 篇占位符残留** |
| `featured_image` 存在性 | 指向的文件在 `static/` 里不存在 | **931 篇坏配图** |
| summary 长度 | < 60 或 > 200 字符 | 327 篇过短 |
| 来源白名单 | 不来自 `links.original` 允许域 | 合规红线落地为代码 |

**注意最后一条**：`RUNBOOK` 里的"合规红线"今天只是**文字**，靠会话自觉遵守。变成域名白名单后，它才是**门禁**。

### 3.6 把 `public/` 移出仓库

现状：`git add -A content && git add -A public`，`public/` 已提交 51,940 个文件，每次发布重写上千文件 → 5 分钟构建、巨大 diff、`.git/index.lock` 事故、无意义的 `git log`。

目标：CI 构建，产物进 CDN，不进版本库。

```yaml
# .github/workflows/build-deploy.yml（示意）
- uses: actions/checkout@v4
- run: hugo --minify          # 需要 extended 版（模板里有 SCSS）
- uses: amondnet/vercel-action@v25   # 或 deploy hook curl
  with: { vercel-token: '${{ secrets.VERCEL_TOKEN }}' }
```

收益：仓库瘦身约 90%，构建从本机/NAS 移到云端并行，`index.lock` 事故面**归零**，`deploy.py` 整条 SSH 链路（含明文密码）可以删除。

### 3.7 三层发布闸（这是"自动化"与"质量"的和解点）

| 层 | 内容 | 谁批 | 理由 |
|---|---|---|---|
| **T0 无人自动发** | 早报/日报骨架（聚合 + 署名原文链接）、结构化数据页刷新 | CI | 无创作成分，来源可核 |
| **T1 CI 自动发 + 事后抽检** | 官方 release notes / 论文摘要的改写，带原文链接 | CI（schema 闸通过即发） | 有增量，但事实层来自一手源 |
| **T2 人工过闸** | 含数字、观点、争议、独家判断的深度稿 | **PR 待审** | 错了要担责的 |

T2 的评审界面不用另建：**GitHub PR 天然提供 diff、评论、回滚。**

这条同时回应 review §3.3 的 scaled content abuse 风险：T0/T1 是"带署名的聚合"，T2 才需要人的判断。**把"AI 改写"整体归入自动化发布，才是政策风险所在；分层之后风险被限制在可辩护的那一层。**

### 3.8 审计轨迹：每次运行写一个 JSON

`state/runs/<ts>.json`：`{items_seen, adopted, rejected:[{id, reason}], tokens, cost_usd, duration}`，并在提交信息里带 run id。

意义：把"agent 会话不可审计"这个结构性问题就地消解。**没有这层，"为什么今天只有 2 篇"永远查不出来。**

## 4. 失败矩阵

| 失败模式 | 现状 | 目标 | 可自愈 |
|---|---|---|---|
| 采集源挂 / 改接口 | 静默降产 | 非零退出 → workflow 失败 → webhook | 否，但 5 分钟内可见 |
| LLM 限流 / 欠费 | 静默降产 | 重试 3 次 → 降级确定性轨 | **是** |
| 构建失败 | push 前拦截（唯一做对的） | 同，且 main 不被污染 | 否，阻断 |
| Vercel 卡队列 | 手动推空提交 | 发布后 3 分钟自检 GET + 自动重试一次 | **是** |
| 站点停更 | **37 天无人察觉** | 6h 心跳 dead-man switch | 否，但当天可见 |
| 密钥泄露 | 无扫描 | gitleaks CI + 停止提交 `public/` | 否，但提交前拦截 |

看门狗最小实现（约 10 分钟，零成本）：

```yaml
on: { schedule: [{ cron: '0 */6 * * *' }] }
- run: |
    age=$(( ($(date +%s) - $(git log -1 --format=%ct -- content)) / 3600 ))
    [ "$age" -lt 6 ] || curl -s "${{ secrets.ALERT_WEBHOOK }}" -d "neican 停更 ${age}h"
```

## 6. 落地顺序（含验收标准）

| Phase | 内容 | 工作量 | 验收（可证伪） |
|---|---|---|---|
| **0** | P0 凭据处置（删 `ads/unit.html` 第 1 行、轮换 NAS 密码 + PAT）+ 看门狗 + 失败通知 | 30 分钟 | 人为把 `content/` 最后提交时间改老 → 15 分钟内收到告警 |
| **1** | 关掉 `public/` 提交，改 CI 构建发布 | 半天 | 仓库体积降约 90%；一次内容提交 3 分钟内上线 |
| **2** | L0/L1 + 无 LLM 早报日报 | 1 天 | **PC 关机 48 小时，站点照常更新** |
| **3** | L2 增强轨 + schema 闸 + T0/T1 | 1 天 | 构造一条坏 frontmatter → 被拒绝且 JSON 里写明原因 |
| **4** | 存量治理批处理 + 常青数据层 | 持续 | 931 配图 / 4,904 占位符 / 634 分类 / 65 组重复标题 / 146 个 `-` 开头文件名，逐项收敛 |
| **5** | agent 降频至 1–2 次/天，只做审阅 | — | agent 会话里不再出现 `deploy.py` 调用 |

**顺序不可交换**。理由：
- Phase 0 必须最先——**在能观测之前做自动化，等于自动化一个黑箱**（这正是 37 天事故的成因）。
- Phase 1 必须早于 2/3——否则自动化只会更快地制造大 diff 和锁冲突（现状 `deploy.py` 里那段 `.git/index.lock` 守卫就是这个病的症状）。
- Phase 5 放最后——先把确定性轨跑稳，再撤掉会话说。

## 7. 明确不做（反模式）

1. **不把 agent 放进 cron。** 它做判断，不做轮询。
2. **不让 agent 直接 push main。** T2 走 PR，T0/T1 由 CI 提交且单提交可回滚。
3. **不做"每 30 分钟必须产出"的 SLA。** 会话量 13–53/天时，没有观测数据能支撑任何频率结论。
4. **不在没有告警的情况下自动化。**
5. **不把状态放进会话记忆或"grep 全库"。**
6. **不重建"n8n 式"的节点 JSON**，也不重建"会话式"的黑箱——两者是同一个错误的两面。

## 8. 一个必须先验证的风险

**采集层的可达性未经证实。** aihot.news 与国内官方源在海外 runner 上是否被限流/拒答，尚未实测。这直接决定 L0 放云端还是放 NAS。

## 9. 需要你拍板的三件事

1. **LLM key 用哪家？** 它同时决定"生成放云端还是 NAS"与成本口径。可选：国内模型（成本低、NAS 可达、runner 基本可达）或 OpenAI/Anthropic（质量高、仅 runner 可达）。→ 若选后者，则 L0 采集与 L2 生成必须同处云端，不能拆。

## 10. 决策记录：与 n8n 的关系（2026-09-11）

**结论：本方案不是"放弃 n8n"，而是把它拆成四件事分别处置——方法论全继承，生产编排权收回，观测职责剥离，实验角色保留但零权限。**

| 层 | 处置 | 理由 |
|---|---|---|
| 方法论（分类闸 / 四维加权评分 / 结构五型 / 写作规范） | **全量继承** | 已逐条提取进 `SPEC-selection-and-style-2026-09-11.md`。这是 2025-06 就成型的编辑资产，与执行引擎无关，丢掉才是损失。 |
| 生产编排权（调度 / 生成 / 发布） | **退出，且要求物理不可恢复** | 发布权必须归属单一、可 diff、可审计、可评审的通道（§3.1 / §3.6 / §3.7）。n8n 有两条本次事故的实证硬伤：`database.sqlite` 7.6 GB（执行历史无界 ⟺ 不可观测）、`restart: "no"`（宿主机一重启就不回来）。 |
| 观测 / 告警 | **明确不承担** | 见 §10.1。 |
| 实验 / 探索 | **允许保留，但零发布权** | `192.168.50.224:30109` 那台本就与内容生产无关。约束：只产出 spec / 代码 / 报告，不能 commit、不持有任何发布凭据。 |

### 10.1 为什么看门狗不能交给 n8n（反驳 HANDOVER §7 P1）

HANDOVER §7 P1 的候选解法 B 写着"至少加'6 小时未更新→飞书告警'的看门狗（**n8n 可担任**）"。这条不成立，两条证据都在 HANDOVER 自己身上：

1. **`restart: "no"`** —— NAS 重启或容器崩溃后 n8n 不会自行恢复。**一个需要被观测的进程，不能承担观测职责。** 而"6 小时未更新"最常见的成因之一，恰恰就是宿主机重启。
2. **它的历史战绩**是连续 5 周每天失败 30–50%、无人知晓。37 天停更正是这么发生的。让病人当医生。

正确形态是**心跳倒挂（dead-man's switch）**，不是轮询：

- 每次成功发布后，流水线**必须**向外部 heartbeat 端点报告一次；**没收到报告 = 告警**。
- 方向反了。轮询是"我去问站点更新了没有"，心跳是"你没交货我就知道"。前者在检查器自己死掉时静默失效；后者不会，因为检查器在第三方。
- 覆盖面反而更广：整条链（本机 → CI → CDN）任一环死掉都不会有心跳，包括"站点还活着但内容是 3 天前的"这种轮询查不出的状态。
- 零自建：不需要再养一个常驻服务、再维护一个数据库。

### 10.2 唯一有条件保留的位置：国内出口（采集层）

对应 §8 那条待验证风险：若 aihot.news / 国内官方源在海外 runner 上不可达，需要一个国内执行器。**但形态建议是 NAS 上的 cron + Python 脚本，而不是 n8n。**

理由：这一层只做三件事——拉 RSS/API、算指纹、写 `state/inbox.jsonl`。n8n 的连接器库在这里没有增量能力（`feedparser` + `requests` 足够），却会重新引入**第二个编排事实源**——那正是 §3.1 要治的病：调度器出现在两个地方，两边说法还不一致。

该层的硬约束（无例外）：只允许写 `state/*.jsonl`；**不 commit、不 push、不持有发布凭据**；调度同样写在版本化文件里（`deploy/systemd/*.timer` 或 compose），不写在控制台里。

### 10.3 一个连锁收益：PAT 轮换 = 旧 n8n 的物理关机

旧工作流的发布能力来自**硬编码在 3 个工作流里的 GitHub PAT**。因此 §6 的 Phase 0（吊销 + 换 fine-grained PAT + 存 GitHub Secrets）不只是安全修复，它同时是**结构性 kill switch**：即便有人误点旧工作流的 Publish，push 也必然 401。

**"防双写"不该依赖 `active=0`** —— 那是一个能被一次误操作、一次数据库迁移、一次备份回滚推翻的状态位。凭据撤回才是物理约束。

### 10.4 新发现：n8n 存档本身是凭据载体（不可直接入库）

实测 `D:\Work\n8n\` 的 21 个 JSON：`hugo_sync_workflow.json` 含明文 `ghp_`，`AI____.json` 含明文 `tvly-`（Tavily key）。

所以"把旧工作流归档进仓库以便日后考古"这个动作**不能直接做**——仓库是公开的（`github.com/huangzuomin/AInews`），直接提交等于二次泄露。正确顺序：
