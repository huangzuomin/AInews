# neican.ai 改造方案第三方评估（Review of ZCode's Plan）

> 评估时间：2026-09-10 夜
> 评估对象：`newsroom/HANDOVER.md`（ZCode 撰写的诊断与改造交接文档）
> 评估方法：全部结论基于本机与线上的**实测证据**，不采信文档自述；对无法验证的部分明确标注。
> 阅读提示：本文档与 HANDOVER 并列使用。**§1 是与 HANDOVER 不一致的事实清单，请优先读。**

## 0. 判决摘要

| 维度 | 判断 |
|---|---|
| 诊断部分（§3 旧系统故障清单） | **基本成立**。停更根因（单一供应商 + 无告警）、成本倒挂、单一写入者缺失、凭据裸奔——都指向真实病灶。 |
| 改造原则（§4.1 五条） | **方向对，但两条自己没做到**：原则 3「失败必须可见」= 未建设；原则 5「规范进文件」= 文件被 `.gitignore` 排除。 |
| 落地形态（§4.2 产线） | **选了最脆的执行层**：agent 现场值班 + 单人 PC cron。它复刻了自己否决 n8n 的同一个缺陷（不可 diff / 不可测试 / 不可回滚）。 |
| 运维与部署（§4.3、§9） | **过度耦合**：为了在"不能构建的地方构建"，付出了 NAS SSH 密码、4-5 分钟构建、3.0GB 仓库、5 万文件 push 的代价。 |
| 风险清单（§7） | **漏了 3 条**：NAS SSH 密码泄露、磁盘/机器环境风险、分发层完全缺失。 |
| 收益思路（§5） | **公式对，约束判断错**。当前约束是"分发与收录"，不是"产量"；方案把 100% 工程量投在非瓶颈环节。 |
| 优先级排序 | **顺序反了**：核心事故是"静默停更 37 天"，修复项却是广告位（P2），告警（P1）未动。 |

**一句话总结**：这不是一个"更优方案"的问题，而是一个**做多了**的问题。当前系统在产量维度上已经过剩 2 个数量级，真正的空缺是索引、内链、资产整治、告警——四件事都不需要新产线。**优雅的重构方向是净删代码，而不是换一层更多组件。**

## 1. 事实核验：与 HANDOVER 不一致或文档未发现的部分

### 1.1 P2"广告位不渲染"的根因不是 `findRE`（已定位并实测修复）

| 项 | 内容 |
|---|---|
| HANDOVER 说法 | "模板注入逻辑在构建中不生效……排查 `layouts/partials/ads/unit.html` 与 `layouts/_default/single.html` 的注入逻辑；`findRE/strings.TrimPrefix` 用法待验证" |
| 实测结论 | **注入逻辑写在一个从未被执行的模板里。** 文章页实际由 `layouts/page.html`（项目根级，2025-06-21 创建）渲染；`layouts/_default/single.html`（今天新写的）**从未参与渲染**。 |
| 证据 1 | 线上与本地构建的文章页含 `color: #999` 日期侧栏（`layouts/page.html` 独有），且**不含** `_default/single.html` 独有的 `instapaper_ignoref b helvetica tracked ttu` 分类侧栏。 |
| 证据 2 | 构建产物中不存在 `_default/single.html` 里的 `<!--ADDEBUG …-->`、`ad-slot`、`<ins class="adsbygoogle">`（只有 head 里的加载器脚本 1 处）。 |
| 证据 3 | 实验：把注入逻辑放进 `layouts/page.html` 后，两个广告位**立即渲染**（2 个 `<ins>`，slot `7719468603` / `1594607058`，无 HTML 转义、无残留）。 |
| 证据 4 | 实验：移走 `layouts/page.html` 后，`layouts/_default/single.html` 才接管渲染（此时广告位才出现在产物里）。 |
| 附带发现 | 日报页由 `layouts/newspaper/single.html` 渲染，早报同理；即项目里同时存在 4 套近似重复的内容模板（`page.html` / `newspaper/single.html` / `morningnews/single.html` / `_default/single.html`），改错文件是**结构性必然**，不是偶发失误。 |
| 版本注记 | 生产构建用 `hugomods/hugo:latest`（本次产物为 0.161.1），本地验证用 0.147。Hugo 0.146 重写过模板系统，而本站模板混用新旧两代写法 —— 这也是"改了不知道有没有生效"的温床。**建议固定构建镜像版本 + 在流水线里断言渲染来源。** |

### 1.2 泄露凭据不止 1 处，第 2 处更严重（文档未发现）

- `layouts/partials/ads/unit.html` 的**第 1 行**是 ``;ZqxJB`1``，与 `newsroom/config.json` 的 `ssh_password` **逐字节相同** —— 即 **NAS SSH 登录密码（sudo 密码级凭据）**，被误粘贴进了模板文件。
- 该文件已被 git 跟踪（`git ls-files` 可见），而仓库是 **public**。
- 幸运点：`HEAD` 版本的首行是正常注释，说明这行是**工作区未提交的改动**，尚未推送。`deploy.py` 只 `git add -A content public`，所以也没被顺带提交。
- ⚠️ **风险闭环提醒**：任何一次手工 `git add -A` / `git commit -a` 都会把它公开。而且**如果先修广告位、后删这一行，密码会随广告上线到每一篇文章的 HTML 里**（搜索引擎与快照会留存）。这次运维动作有严格顺序要求。

### 1.3 "必须提交 public/" 不是平台限制，是没配构建

HANDOVER §2 写："已验证：只提交源码不提交 public/ 不会触发内容更新"。这是**当时未配置构建命令**的结果，不是 Vercel 的限制。为绕过它而把 `public/` 提交进仓库，代价实测：

- 仓库体积 **`size: 3,164,640 KB` ≈ 3.0 GB**（GitHub API 实测）
- 每次部署要 `git add -A public` 承载 5 万+ 文件（SMB 上分钟级）
- 历史里还沉淀着 4,968 条模板字面量 commit message、7 条"你的提交信息"

### 1.4 §8.1 的 Actions 免费额度前提错误

HANDOVER 担心"私有库 2000 分钟/月"。实测 `"private": false, "visibility": "public"` ——**公开仓库的标准 runner 分钟数免费且不计量**。真正门槛不是分钟数，而是"写稿必须一次 LLM 调用"，而 ZCode 的能力目前记在订阅里、搬不进 Actions（见 §4.1）。

### 1.5 值班自动化不在可审计的位置（文档未发现）

HANDOVER §4.2/§9 引用的 `automation-ea60dfb0-9b17-4a08-8b1f-24db73f19123` 在**本机自动化登记表里不存在**（本机仅 2 条无关且已暂停的自动化）。也就是说：**产线的触发条件、上下文、提示词、判据，存放在一个第三方 agent 产品的会话状态里，无法备份、无法审计、无法交接**——这与 §9"关键文件与操作指引"的承诺不符。

### 1.6 内容资产健康度审计（文档未做，实测数字）

对 9,976 篇内容（洞察 9,376 / 日报 321 / 早报 279）逐篇解析 frontmatter：

| 问题 | 数量 | 后果 |
|---|---|---|
| `main_topics` 出现 **634 个不同取值**（RUNBOOK 规定 7 个） | 634 | 634 个分类页，绝大多数只有 1-2 篇，互不连通 → 内链主干被稀释、爬虫噪音 |
| `featured_image` 指向**不存在的文件** | **931** | 坏图 / 空 og:image |
| frontmatter 含字面量 `\n` | 812 | 字段污染 |
| 标题完全重复（同事件多源重复成文） | **65 组** | 重复内容信号 |
| 文件名以 `-` 开头（URL 如 `/insights/-27-bugclaude…/`） | 146 | 低质量 URL 形态 |
| summary < 60 字符 | 327 | SEO description 无效 |

### 1.7 仓库卫生：根目录压着一整套"旧原型站"（文档未发现）

仓库根目录同时存在：`index.html`（Hugo 0.161.1 生成的"模板迁移版"首页，内含 `Round 6 A Insight` / `Fixture summary` 等**测试夹具数据**）、`briefs/`、`topics/`、`entities/`、`concepts/`、`timeline/`、`categories/`、`tags/`、`about/`、`explore/`、`all-categories/`、`newspaper/`、`insights/`、`404.html`、`sitemap.xml`、`index.xml`，另有 `public-test/`。

这些与 `public/` 里的正式产物**同域、同名、不同源**。当前因为只发布 `public/` 而侥幸无事；一旦 Vercel 的 Output Directory 配置被改动或重建项目，线上会直接变成那个含测试数据的原型站。这是**悬在头顶的低概率高损失风险**。

### 1.8 机器环境风险（文档未发现）

- **C 盘可用空间实测 1.07GB**（本次评估做本地构建验证时一度把 C 盘写到 0 字节，已清理临时产物恢复）。
- ZCode 值班就跑在这台机器上。磁盘写满会以"什么都没发生"的方式停刊——而这恰好是 HANDOVER 最在意的那类故障（静默停更）。
- 这类风险写进 §7 的"P1"比广告位更值钱。

## 2. 第一性原理：北极星是广告收益，但约束不在产量

### 2.1 把公式代入基线数字

```
月收入 = 月会话数 × 人均页数 × RPM / 1000
```

- 实测基线：28 天 **$0.36**。
- 取中文科技站较乐观的 RPM = $1.5 → 月会话 ≈ **240**，即 **≈8 次会话/天**。
- 取保守 RPM = $0.5 → 月会话 ≈ 720，即 **≈26 次会话/天**。

**结论：这个站此刻的约束是"被发现"，不是"被生产"。**

### 2.2 方案的投入分布与约束错位

| 环节 | 现状 | 方案投入 | 对北极星的边际影响 |
|---|---|---|---|
| 产能 | 旧 23 篇/天 → 新 3-10 篇/天，仍远超需求（8 次会话/天） | ★★★ 几乎全部工程量 | ≈ 0 |
| 收录/分发 | GSC 未接、sitemap 未提交、无外链 | ☆ 0 | **决定性** |
| 人均页数 | 9,976 篇之间几乎没有可用内链（634 个碎分类） | ☆ 0 | **决定性** |
| RPM | 广告位空置（已定位）、无 minify、6,420 张未优化图片 | ★ 广告位算 1 项 | 中等 |

约束理论：**在非瓶颈环节优化，产出的是库存，不是收益。这里的"库存"就是 9,376 篇无人阅读的文章。**

按这个框架，HANDOVER §8 的问题 2「哪个频率×质量组合最优」本身是个假问题——**频率对收益的弹性在当前量级下近似为零**；有弹性的只有"被收录的页面数"和"每次会话的页数"。

### 2.3 由此推出的三条真正能动的杠杆（都不需要新产线）

1. **被收录**：GSC 接入 + sitemap 提交 + 清理 634 个碎分类 / 931 个坏图 / 65 组重复标题（对爬虫而言这是"这个站不值得信任"的信号）。
2. **一个页面承接多个查询**：常青/结构化页面（对比表、时间线、术语、实体页）。新闻页生命周期 24-72 小时；常青页 12-24 个月。对一个会话量几十的站，**只有常青层能复利**。
3. **人均页数**：模板级相关文章（tag 交集即可，不需要 embedding）+ 站内搜索入口 + 日报↔洞察互链。

注意：这三条恰好是 HANDOVER §5 自己写的公式因子，却在 §7 里被列为 P3（内链）或根本没出现（GSC 是 P2 但被广告位排在后面）。**方案与自己的框架不一致。**

## 3. 逐条批判 ZCode 方案

### 3.1 两处自相矛盾（这是方案最需要修的地方）

**矛盾 A：版本控制的边界画反了。**
原则 5 是"提示词与规范进文件"，落地成 `newsroom/RUNBOOK.md`。但 `.gitignore` 里有 `newsroom/` —— **最该被 diff、评审、回滚的东西（值班手册、提示词、部署脚本、配置模板）不在版本控制里；而一个含 NAS 密码的模板文件在公开仓库里。**

**矛盾 B：用新载体复刻了自己否决的缺陷。**
否决旧 n8n 的理由是"功能/提示词/正则封在节点 JSON：不可 diff、不可测试、不可回滚；本次所有生产事故都源于此形态"。
但新方案的核心是"值班 agent 现场判断、现场写稿、现场调工具"——**同样不可 diff（散在多轮对话里）、不可测试（同一输入两次输出不同）、不可回滚（没有"上一版产线"可回退），而且比 JSON 更不可审计**。同一问题换了载体，没有解决。

**矛盾 C（附带）：原则 3 空转。**
"失败必须可见"在 §7 里被自己标注为"无告警体系，未建设"。而"停更 37 天无人察觉"是本项目最大的历史事故——今天先做了广告位（P2），把告警（P1）留着。**优先级与事故史相反。**

### 3.2 执行层选型：不是"已知接受"，是架构性错误

HANDOVER §7 P1 把"PC 关机 = 停刊"写成"已知接受中"。但它同时违反了自己的原则（失败不可见）：

- 把"唯一写入者"绑到"唯一一台会关机的机器"上，等于每天固定开一个停更窗口；
- 该机器还有 1.07GB 可用空间（§1.8）；
- 产线配置存在第三方产品会话里，不可备份（§1.5）。

**这三条叠加，不是"接受风险"，是"没有系统"。**

### 3.3 部署路径把 5 个无关组件串成一条链

```
Windows 本机 → paramiko → NAS SSH（明文密码）
  → sudo -S 从 stdin 喂密码 → docker run --rm → hugo 构建 4-5 分钟
  → git add -A content && git add -A public（5 万+ 文件）→ push 3.0GB 仓库
```

其中只有"hugo 构建"是必需的，其余都是为了在"不该构建的地方构建"而付的税。具体问题：

- `sudo -S -p ''` 把密码从 stdin 喂进去：任何回显/日志都会带出密码；
- `git add -A content && git add -A public`：`-A` 会把任何被误放进这两个目录的东西一起上线（今天 unit.html 的密码行若不是在 `layouts/` 而是在 `content/`，此刻已经在线上了）；
- SMB 上的分钟级 git 操作，就是"git 锁文件事故"的土壤。

### 3.4 去重靠 grep：O(n) 且无语义

RUNBOOK 要求写稿前在 9,376 个文件里 grep 标题关键词。既慢，又无法命中"同一事件的不同表述"——65 组重复标题就是证据。正解是一张 append-only 的 seen 表（规范化 URL 哈希 + 标题指纹），O(1) 查询、可审计、可回放。

### 3.5 内容策略的战略风险（比技术风险更大）

- **同质化**：信源是一手英文（MarkTechPost / X / 官方博客），产出是中文事件复述。这与机器之心、量子位、新智元的日常产出同质，而对手有品牌、渠道、团队。以 neican.ai 现在的域名权重，**快讯类查询拿不到排名**，这块产能注定不自带流量。
- **平台风险**：以第三方聚合器为信号 + 规模化 AI 生成 + 无增量价值，正落在 Google「scaled content abuse」的射程内；AdSense 本身也会对低价值内容降权/限流 —— 直接打击北极星。
- 文档里"质量就是流量"与"按门槛低成本批量生成"两个命题是**互相抵消**的，必须二选一。

## 4. 更优雅的重构方案

**一句话：把"生产"降级为确定性代码，把"判断"上移给 agent，把"分发"提到第一优先级。**

### 4.1 四层结构（每层单一职责，可独立测试与替换）

| 层 | 职责 | 实现 | 是否依赖 LLM |
|---|---|---|---|
| **L0 采集与状态** | 拉取、规范化、去重、排队 | 30-60 行 Python：aihot（排序信号）+ N 个一手 RSS/官方 changelog（事实底稿）→ `state/seen.jsonl`（norm_url_hash / title_fp / first_seen / article_path）→ `state/queue.json` | 否 |
| **L1 成稿** | 模板化起草 + schema 校验 | `scripts/draft.py --queue`：固定提示词模板（进版本库）+ 结构化输出 + 多供应商 fallback；失败写 `state/errors.jsonl`（不静默） | 是（一次函数调用，不是"会话"） |
| **L2 构建发布** | 构建、部署、变更通知 | CI 内 `hugo --minify`；**不再提交 `public/`**；主机侧只做一次配置（Vercel 指向构建产物，或换原生支持 Hugo 的 Cloudflare Pages / Netlify，零配置） | 否 |
| **L3 观测** | 心跳与告警 | 每次发布成功打一次 dead-man's switch；外部定时器"没收到就告警"；每日健康摘要（发布数 / 失败数 / 队列长度） | 否 |

**人（agent）只做 CLI 做不到的两件事：**
1. **每日抽检**：随机 2 篇 + 当日 top1，打开原文核对事实，出抽检报告。—— 这正是 ZCode 相对 Dify 的真优势，应该用在这里，而不是用在"每 30 分钟决定写什么"。
2. **每周复盘**：选题结构、被收录页面、RPM 变化 → 回改提示词与门槛（写回版本库，可 diff）。

### 4.2 拆开"永不断线"与"有判断力"（关键取舍）

Actions 迁移的真实门槛不是分钟数（§1.4），而是"写稿需要 LLM 调用" → 需要一个 API key → 把"边际 0"变成"计量计费"。**因此不要整体迁移，而要拆分**：

- **生命线（必须 100% 可用）**：早报 / 日报骨架用确定性渲染（不需要 LLM：标题聚合 + 时间排序 + 模板），CI 全权负责 → **站点永不因 PC 关机而停更**。
- **增量（可有可无）**：深度洞察由本机 agent 或本地脚本产出，断供只损失增量，不构成事故。

这一拆分同时解决三件事：PC 关机不再是事故；不再需要 agent 每 30 分钟"空转"；成本风险不再藏在订阅定价里。

### 4.3 必须删除的清单（优雅 = 减法）

| 删除项 | 收益 |
|---|---|
| `deploy.py` + paramiko + NAS SSH 密码 + sudo 喂密码 + docker 构建 | **净删约 70 行代码与一条凭据**；部署退化成 `git push` |
| `public/` 入库 | 仓库 3.0GB / 5 万文件 → 约 20MB / 源码：clone、push、diff 全部变秒级 |
| 根目录旧原型站静态产物（§1.7 全部条目）+ `public-test/` | 消除"线上可能变成测试站"的低概率高损失风险 |
| 4 套近似重复的内容模板，收敛为 1 套 + 数据驱动差异 | "改错文件"这类 bug 结构上不再可能 |
| 634 个碎分类 → 7 个 | 内链主干重建；爬虫噪音下降 |
| 931 篇坏图引用 / 65 组重复标题 / 146 个 `-` 开头 slug | 资产健康度；重复内容信号 |
| `static/` 中绝大多数旧图片（6,420 jpg） | 页面体积与仓库体积 |
| `hugomods/hugo:latest` 的浮动 tag | 固定版本，消除渲染漂移 |

**新增项极少**：`state/`、`scripts/`（fetch / draft / publish / healthcheck 四个小脚本）、`.github/workflows/`、`templates/`（提示词）。全部进版本库。

### 4.4 迁移路径（可逆、分步）

1. **不动产线**，先把 `public/` 从"唯一发布通道"降级为"构建产物"（配置 Vercel/CF Pages 构建一次，验证线上一致）。
2. 停止提交 `public/`，删除根目录旧原型产物；仓库瘦身。
3. 部署改 `git push` 或 CI；`deploy.py` 退役。
4. L0 状态表上线（替换 grep 查重）。
5. 生命线（早报/日报）确定性化并交给 CI。
6. 最后才谈洞察层的起草模板化与多供应商 fallback。

每一步都可以单独回退（保留 `git bundle` 备份与旧 NAS 路径）。

## 5. 对 HANDOVER §8 八个问题的直接回答

**1. 执行层选型** — PC cron 不可接受（单点 + 不可审计 + 磁盘近满 + 配置不在版本库）。Actions 可行且 **public 仓库分钟数不计费**；真门槛是需要一个 LLM API key。因此**不整体迁移**，而是按 §4.2 拆分：生命线确定性化上 CI，判断力留在本机作为增量。构建与部署一律上云。

**2. 更新频率策略** — 假问题。§2.1 的数学说明当前约束不在频率（8 次会话/天）。建议固定两次/天的**确定性脉搏**（早报 / 日报）+ 不定量洞察；任何"提高频率"的主张都需要先给出"新页面被收录 → 带来会话"的证据链。

**3. 内容策略** — 双层不够，缺第三层。新闻层（生命周期 24-72h，拼不过大站）+ 综述层（已有）+ **常青资产层**（唯一能复利的）。常青层直接用现有语料做：模型/价格/上下文成本对比表、发布时间线、术语表、实体页。你已经有 `entities / concepts / timeline` 的旧结构痕迹和 9,976 篇带日期语料——这是别人抄不走的资产。2026 年中文 AI 资讯站的有效策略不是"更快地转述英文新闻"，而是"把噪音沉淀成可引用的事实索引"。

**4. 看门狗最小实现** — 发布成功后 `curl` 一次外部 dead-man's switch（healthchecks.io 免费档），由外部定时器负责"没收到心跳→告警"；国内可达备选取 ServerChan（一个 GET）或飞书机器人 webhook。**零常驻服务、十分钟完成。不要用 n8n 承担**——那等于把刚拆掉的系统又请回来。

**5. 广告位渲染 bug** — 不是 `findRE` 的问题，是模板没被执行。修复见 §6，已实测。

**6. 安全** — 处置清单需补三条：
   ① 除 PAT 外，**`layouts/partials/ads/unit.html` 第 1 行的 NAS SSH 密码**必须一并轮换与移除（sudo 密码级凭据，爆炸半径大于 PAT）；且**必须先删该行再修广告位**（否则密码随广告上线）。
   ② 8 字符密码 + 密码登录 + `sudo -S` 喂密码 → 改**密钥认证 + 专用非 root 用户 + 不授予 sudo**（只给静态目录写权限或 docker 组）。
   ③ 鉴于仓库公开且历史里沉淀着 4,968 条模板字面量 commit message，**建议直接重建仓库**（单次初始提交，只含 `content/ layouts/ themes/ scripts/ hugo.toml` 等源码），而不是在 3GB 历史上跑 `filter-repo`。本地留 `git bundle` 归档即可。这一举同时解决：凭据残留、垃圾历史、仓库膨胀。

**7. 合规** — 现在的抗辩是弱的：RUNBOOK 自己写"事实只能来自信源摘要/原文"，而成稿事实上是 aihot 的 AI 摘要再改写（§7 P3 也承认"未逐篇打开原文核实"）。两条路：
   ① 把一手 RSS / 官方 changelog 变成**主信源**（aihot 只保留排序作用）——更根本，顺带解决单一信源风险；
   ② 直接去要书面授权（对方是小站，多半乐于给）。
   建议 ① 为主、② 为辅。

**8. 遗漏项（对北极星有实质影响）**
   - **索引层完全缺失**：GSC、sitemap 提交、robots、canonical 复核，可选 IndexNow 推送新 URL。这是当前唯一的真约束。
   - **内链层完全缺失**：9,976 篇之间几乎无可用内链。模板级"tag 交集相关文章"是投入产出比最高的单项改动（比 embedding 更该先做）。
   - **资产整治缺失**：634 个碎分类 / 931 个坏图 / 65 组重复标题 / 146 个非法 slug —— 对排名的影响大于再写 100 篇新稿。
   - **页面体验**：未启用 `--minify`；6,420 张未压缩图片；AdSense 也看 CWV。
   - **备份与可恢复性**：`content/` 实际只有 NAS 本机 + GitHub 两处，无独立快照。建议每周 `git bundle` 到 NAS/网盘。
   - **成本结构的隐性项**：ZCode 订阅被当作"边际 0"，但 agent 每次值班都要长上下文加载 + 多轮工具调用，48 次/天。一旦订阅额度或价格变化，边际成本立刻变成实数——**把全部判断押在订阅上，等于把成本风险藏在别人家的定价里**。

## 6. 已验证的修复补丁

### 6.1 广告位（实测通过）

前置步骤（**顺序不可颠倒**）：

**(a) 删除 `layouts/partials/ads/unit.html` 第 1 行**（该行是 NAS SSH 密码，不是模板语法的一部分）。
> 同时处置：轮换 NAS 密码 + 轮换 GitHub PAT（fine-grained，仅 `AInews` 的 contents:write）。

**(b) 把注入逻辑放进真正生效的模板 `layouts/page.html`**，替换其中的 `{{- .Content -}}`：

```gotemplate
{{- $content := .Content -}}
{{- $adTop := partials.Include "ads/unit.html" (dict "slot" site.Params.adsense.slot_after_tldr "cls" "ad-slot ad-slot-top") -}}
{{- if and $adTop (strings.Contains $content "</blockquote>") -}}
  {{- $content = replaceRE "(?s)(</blockquote>)" (printf "%s$1" $adTop) $content 1 | safe.HTML -}}
{{- end -}}
{{- $content -}}
{{- partials.Include "ads/unit.html" (dict "slot" site.Params.adsense.slot_footer "cls" "ad-slot ad-slot-footer") -}}
```

要点：
- 用 `replaceRE` **一次替换**取代 `findRE + strings.TrimPrefix` 拼接（后者还有个隐藏 bug：`printf` 返回 `string`，Hugo 会**转义 HTML**，必须 `safe.HTML`；现有代码没走到这一步是因为它从未被执行）；
- 文末位当前会落在 `## 引用` 标题之后、脚注列表之前。若嫌突兀，可改为在 `## 引用` 之前插入，或干脆放在 `.Content` 之后（可接受）；
- 更彻底的做法：让生成器在正文里埋 `<!--AD_SLOT_TOP-->` 标记，模板只做 `replaceRE` 替换 —— 广告位从此与正文结构解耦。

**验证结果（本地 0.147 构建 + 线上产物比对）**：`<ins class="adsbygoogle">` ×2、`data-ad-slot` = `7719468603` / `1594607058`、`ad-slot-top` / `ad-slot-footer` 各 1、HTML 转义 0 处、密码残留 0 处。

### 6.2 其它

**(c)** 删除或明确标注 `layouts/_default/single.html`（死模板）；把 4 套内容模板收敛为 1 套。

**(d) 流程补丁（防止同类问题复发）**：在每个内容模板里埋 `<!--RENDERED_BY:page.html-->` 之类的标记，构建后用一条 grep 断言线上 HTML 中出现。**"改了没生效"从此可被自动拦住** —— 这是本次 bug 最有价值的教训，值得进 QC 清单。
