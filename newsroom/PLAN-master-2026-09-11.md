## 0. 一页总览

### 0.1 目标态（一句话）

> **把流水线造成一台可重放的确定性机器；把"判断"压缩到两个地方——一个配置文件，和一个人。**
> 内容侧同时满足「可发现（SEO）」与「可引用（GEO）」，且二者由**同一套门禁**保证。

### 0.2 七条工作流（并行轨）

| 轨 | 名称 | 一句话职责 |
|---|---|---|
| **T1** | 凭据与安全 | 让旧产线物理失效，让密钥离开仓库 |
| **T2** | 仓库与构建 | 让构建可重放、让仓库只装源文件 |
| **T3** | 发布通道与观测 | 单一发布通道 + 心跳倒挂告警 |
| **T4** | 采集与归并 | Source → Event，去重变事件归并 |
| **T5** | 生成与门禁 | 双轨生成，过 G1/G2/G3 才准入库 |
| **T6** | SEO / GEO | 三层可引用性（L1 发现 / L2 解析 / L3 引用） |
| **T7** | 主编台与存量治理 | 人的位置 + 9,383 篇历史欠账 |

### 0.3 七个相位

| 相位 | 名称 | 目标 | 退出条件 |
|---|---|---|---|
| **P0** | 止血与可观测 | 密钥离仓、告警上线、静默失效修复 | 人为制造故障 → 15 分钟内收到告警 |
| **P1** | 仓库与发布通道 | `public/` 出仓、CI 构建发布、SEO/GEO 模板层上线 | 一次内容提交 3 分钟内上线；仓库体积降一个数量级 |
| **P2** | 无 LLM 骨架轨 | 不接 LLM 也能出早报/日报 | **PC 关机 48 小时，站点照常更新** |
| **P3** | 判断轨 | 分类闸 + 五维打分 + 配额 + 留痕 | 每次选题都能给出"为什么是它"的理由链 |
| **P4** | 生成轨与门禁 | 证据包 + 结构五型 + T0/T1/T2 | 门禁拦下的稿件有记录且原因可读 |
| **P5** | 主编台与 agent 降频 | Issue 一页审完全天 | 一周不碰 Issue，站点更新不中断 |
| **P6** | 存量治理 | 9,383 篇欠账分批收敛 | 门禁在存量全量上跑通为 0 违规 |

### 0.4 只有两条顺序不可交换

- **P0 必须最先**：**在能观测之前做自动化，等于自动化一个黑箱**——这正是 37 天停更的成因。
- **P1 必须早于 P2/P3**：否则自动化只会更快地制造大 diff 与 `index.lock` 冲突。

其余相位允许并行，但 P4 依赖 P3 的产出契约，P5 依赖 P4 的产出稳定。

`public/` 已从**索引**移除（P1.1，70,505 → 18,066 条目），但它仍存在于**全部历史**里。
后果是实际会挡住发布的：

| 约束 | 阈值 | 当前 |
|---|---|---|
| GitHub 推荐仓库上限 | 1 GB | **2.96 GiB** ❌ |
| HTTPS push 单次上限 | ~2 GB | **2.96 GiB** ❌ 很可能直接失败 |
| CI `actions/checkout` | 越慢越贵 | 560k 对象，必然慢 |

**结论：不做 P1.8，"把发布权交给 CI"这条路在第一步就会卡住。**

## 4. 统一门禁（P0 起生效，P4 全量接入）

```
生成 ──▶ G1 结构 ──▶ G2 事实 ──▶ G3 元数据 ──▶ 发布 ──▶ G3-b 构建后抽检 ──▶ 观测
```

| 闸 | 检查项 | 否决条件 |
|---|---|---|
| **G1 结构** | h2 ≥2；h3/h2 ≤3；正文起始层级 `##`；段长 ≤150；句长 ≤60；TL;DR 存在且语义化；对比内容已表格化 | 任一不满足 |
| **G2 事实** | 数字句带来源比 ≥0.6；一手源比 ≥0.5；来源域名在白名单；无 `YYYY`/`--` 占位符；无未兑现的"来源"承诺 | 任一不满足 |
| **G3 元数据** | `title` ≤30 字；`summary` 80–160 字；`featured_image` 存在；`main_topics` ∈ 闭集；`entities` ⊆ 注册表；`sources` 非空；`slug` 无时间戳后缀 | 任一不满足 |
| **G3-b 构建后** | JSON-LD 可 `json.loads`；`NewsArticle` 必填字段非空；`og:image` 可达（HTTP 200） | 任一不满足 → 阻断部署 |

**G3-b 不可省的理由**：结构化数据是**模板产物**，构建时无法自证。`_internal/schema.html` 的静默失效潜伏数月，正是因为没有人在验产物。

### 4.1 门禁启用时序（实测基线后更正）

**对 20 篇最新文章跑 G1/G2/G3，20/20 全部不达标：**

| 违规 | 篇数 | 说明 |
|---|---|---|
| 缺 `sources` | **20/20** | 无来源索引 → 不可引用。**这不是个案，是产线的常态** |
| `h2` 数量 < 2 | **20/20** | 其中 5 篇为 0——正文从 `###` 起，h1 直跳 h3 |
| `title` > 30 字 | 11/20 | 最长 48 字 |
| 缺 `main_topics` / 不在闭集 | 5/20 | 含 `'AI与科学发现'` 等碎片值 |
| 段落 >150 字 / 句子 >60 字 | 多篇 | 最长段 430 字、最长句 383 字 |

**这条基线推翻了「门禁 P0 起生效」的表述。** 当前产线产出的每一篇都会触发违规——
此刻硬阻断等于让现役产线立即停摆。

更正为两档：

| 阶段 | 门禁模式 | 触发方式 |
|---|---|---|
| **P0–P3** | **warn-only**（只报告，退出码 0） | CI 默认 |
| **P4 起** | **阻断**（违规 → CI 失败） | Settings → Variables 设 `GATES_ENFORCE=true` |

翻转的前置条件是 **P4 生成轨修好**，不是时间到达。G3-b 例外——它从 P0 起就是阻断性的，
因为它校验的是模板产物（与存量内容质量无关），且正是它发现了 newspaper/morningnews
两处 `<time datetime>` 缺失。

## 5. 本轮实测新发现（改变了实施方式）

### 5.1 四个文章模板，只有一个活着（决定 D23）

对构建产物做模板指纹比对（2026-09-11）：

| 页面 | `article-content`（仅 `layouts/page.html` 有；主题里不存在） | `ttu`（仅 `_default/single.html` 有） | `ad-slot-top`（仅 `_default/single.html` 注入） |
|---|---|---|---|
| `insights/*` | 1 | 0 | 0 |
| `newspaper/*` | 1 | 0 | 0 |
| `morningnews/*` | 1 | 0 | 0 |
| `about` | 1 | 0 | 0 |

**结论**：`layouts/_default/single.html`（mtime 2026-09-10 16:54，内含广告位注入与 `<time datetime>`）**对所有页面均未生效**。

这解释了 ZCode 报告里"改了一处没生效"的真实机制：**改动写进了不在查找路径上的模板**。同时意味着广告位从未渲染过（与 REVIEW §2 的独立取证一致）。

**处置**：不逐个修模板（那正是问题本身），而是**把所有 head 级 SEO 出口集中到 `baseof.html`**——它对全部 kind 生效。模板收敛列入 P6.5。

### 5.2 `_internal/schema.html` 不是空的，而是只输出过期微数据（决定 P0.8）

最小复现对照：

```
调用 "_internal/nonexistent.html"  →  Error: no such template  （构建失败，看得见）
调用 "_internal/schema.html"        →  exit 0，产物仅 3 个 itemprop meta，零 JSON-LD
```

Hugo 对**不存在**的模板会硬报错，因此 `schema.html` 是**存在但已退化**的模板：它仍输出 2010 年代式的 `itemprop` 微数据（`name`/`description`/`datePublished`/`dateModified`/`wordCount`/`keywords`），**不输出任何 JSON-LD**。

这比"没有结构化数据"更危险：页面上**看起来**有结构化标记，所以没人去查。而现代消费方（Google 富结果、AI 引擎）主要吃 JSON-LD。

**已实现的替代**（见 §6）。

### 5.3 无 `/search/` 页面（影响 schema 设计）

线上 `/search/` 返回 404。因此 JSON-LD 的 `WebSite.potentialAction`（SearchAction）**必须省略**——否则会指向一个不存在的搜索入口，属于"结构性谎言"，比缺失更糟。

### 5.4 本地首次构建暴露：JSON-LD 被双重序列化（决定 P0.8 的验收方式）

工作树迁到 D 盘后首次跑通构建，抽检产物发现：

```html
<script type="application/ld+json">"{\"@context\":\"https://schema.org\",...}"</script>
```

外层多一个引号、内层引号全部被转义 → `JSON.parse` 必然失败，等于**结构化数据仍然无效**。

**根因**：`<script>` 内 Go `html/template` 的上下文是 JavaScript，而 `jsonify` 返回 `template.HTML`（HTML 上下文类型）。类型不匹配时，Go 会把整段 JSON **再按 JS 字符串编码一次**。

**修复**：`| jsonify | safeJS`（`safeJS` → `template.JS`，与 JS 上下文匹配，原样输出）。

**推论（比这个 bug 本身重要）**：`grep -c 'application/ld+json'` 返回 1 **不等于**结构化数据有效。**G3-b 必须做到 `json.loads` + 必填字段非空**，不能退化成字符串计数——否则会带着"已有结构化数据"的假象上线，重演 `_internal/schema.html` 的静默失效。

### 5.5 CDN 与 origin 被混为一谈（更正 D06）

P1.7 原表述「实测 Cloudflare Pages 国内可达性 → 决定是否从 Vercel 迁」隐含了一个错误前提：
**站点当前没有 Cloudflare**。

实测：

```
$ curl -sI https://www.neican.ai/ | grep -iE 'server|age'
Age: 3828
Server: cloudflare
$ nslookup www.neican.ai
104.21.57.148     ← Cloudflare anycast
172.67.146.165    ← Cloudflare anycast
```

**CDN 层已经是 Cloudflare**，Vercel 只在后面做 origin。

因此：
- 换 origin（Vercel → Cloudflare Pages）**不会改变国内边缘节点位置**——CF 免费版在国内本就走境外节点，与 origin 无关。
- 想真正改善国内访问，需要 **Cloudflare China Network（企业版 + ICP）**，而 `.ai` 无法备案 → 这条路对本项目**关闭**。
- 所以 D06 的真实取舍只是「少一跳依赖」vs「迁移成本」，**不是**"能不能治国内访问"。建议保留现状。

**方法论教训**：把「CDN」和「origin」当成一个决策项，会导出一个看起来在解决可访问性、
实际只是换了一个上游的迁移。**先分层再决策**——可访问性的约束在边缘节点位置，
而边缘位置由套餐决定，不由 origin 决定。

**另一条推论**：`Age: 3828` 说明 CF 缓存了约 1 小时。这意味着**发布后不会立即全球可见**——
验收"发布成功"不能只看源站，要看带 `?cachebust` 的请求或等缓存过期。
这一点必须写进 P1.4 的 deploy 验收里。

## 9. 明确不做（反模式）

1. **不把 agent 放进 cron** —— 它做判断，不做轮询。
2. **不让任何组件直接 push `main`**，除 L3 发布层。
3. **不做"每 30 分钟必须产出"的 SLA** —— 没有观测数据支撑任何频率结论。
4. **不重建节点式编排（n8n 形态），也不重建会话式编排** —— 两者是同一错误的两面：把确定性的事交给不确定的执行者。
5. **不在公开仓库放第三方全文或图片大件**。
6. **不用搜索引擎搜图**。
7. **不让分类由模型自由发挥**（闭集），**不让模型做算术**（权重进配置）。
8. **不追求产量** —— 产量是配额的函数。
9. **不为 GEO 牺牲诚实** —— schema 字段全部从真实 frontmatter 派生，`sources` 缺失留空不臆造。
10. **不发布 `llms-full.txt`**（全量正文再分发风险）。
