## 1. 项目一句话

**neican.ai（AI内参）** 是一个面向中文 AI 从业者的自动化新闻站：实时快讯流 + 每日早报 + 每日晚间日报。
变现方式为 Google AdSense（2026-09 初开通，收益尚在基线水平）。**唯一北极星指标：广告收益最大化**。
运营者：单人（huangzuomin，h.zuomin@gmail.com）。基础设施全部自建/免费档，当前边际成本≈0 元/月。

## 3. 历史诊断（旧系统的故障与缺陷清单，均有证据）

**停更事故（2026-08-04 ~ 2026-09-10，37 天）根因：**
1. **单一 LLM 供应商断供**：评分用 SiliconFlow 的 DeepSeek-V3.2、写作用 Gemini flash-lite，额度耗尽后写作环节整体停摆 → 无新文章 → 全站冻结。
2. **无任何告警**：n8n 此后每天仍执行并失败 30-50%（主要为家宽连 Supabase 的 ECONNRESET），持续 5 周无人知晓。停更是站长自己发现网站不更新才确认的。

**结构性缺陷清单：**
- GitHub PAT（`ghp_YcHR…`，全库读写权限）**明文硬编码**在 3 个工作流的 git push 命令中；Tavily API key、Google CSE cx 同样裸奔。**视为已泄露，轮换仍未完成（见 §7）。**
- 4968 条 commit message 是未求值的模板字面量（`{{ items.length }}`），另有 7 条是未替换的占位符"你的提交信息"——n8n Execute Command 字段未开表达式求值。
- 3 个工作流并发写同一棵 git 工作树；`git pull` 的 remote 名与 push 的 remote 名不一致（AI_news vs AInews）。
- 写文件用 heredoc（内容含 `EOF` 行会静默截断）；部分文章 slug 以 `-` 开头；frontmatter 混入字面量 `\n`。
- n8n 数据库 `database.sqlite` 达 **7.6 GB**（执行历史从不清理）；容器 `restart: "no"`；`NODE_TLS_REJECT_UNAUTHORIZED=0`。
- **成本结构倒挂**：每条 RSS 都生成全文（9369 篇）+ 逐篇 LLM 评分 + 逐篇 Tavily 搜索 + 逐条 Google 搜图，而日报每天只引用 5 篇。绝大多数产出从未被消费，额度就是这么烧完的。
- 早报（7:30）与日报（19:20）两班各自重复跑同一套评分 prompt——纯浪费。
- 同事件多源重复各写一篇（只有 guid 判重，无语义去重）。
- 配图用 Google 搜图下载进 git 仓库：版权风险 + 仓库膨胀。
- 两台机器各有一个 n8n 实例，内容产线在群晖（:5678），容易混淆。

## 4. 改造方案（2026-09-10 落地，即当前 running 系统）

### 4.1 设计原则（从诊断倒推）
1. 漏斗正过来：先筛选后生成，不為落选内容花 LLM 钱。
2. 单一写入者：仓库同一时刻只有一个写方，消除 git 竞争。
3. 失败必须可见：脚本拒绝静默失败；告警体系在路线图上（见 §7）。
4. 零边际成本起步：流量/收益数据说话之前，不花一分钱。
5. 提示词与规范进文件（`newsroom/RUNBOOK.md`），不封在工具节点里。

### 4.2 当前内容生产线（已上线并验证）
```
aihot.news 精选 API（选题雷达，含 AI 评分/推荐理由/原文链接，匿名免费）
   │  ZCode 定时值班（Windows 本机 cron 自动化，每 30 分钟触发，按时间分派班次）
   │  ├─ 06:30 早报班：24h Top 8-10 条 → 一页早报
   │  ├─ 19:30 日报班：基于当日已发内容 + 当日精选 → 综合日报
   │  └─ 其余 46 次/天 → 流水班：score≥70 且未覆盖 → 写 1-3 篇洞察；无新选题则空转秒退
   ▼
newsroom/deploy.py（NAS 上一次性 hugomods/hugo 容器构建 public/ → git add content+public → commit → push）
   ▼
GitHub main → Vercel 自动部署 www.neican.ai（1-8 分钟生效）
```
- 质量纪律（RUNBOOK 强制）：事实只能来自信源摘要/原文、禁止编造数字引语、引用必须给 `links.original`、发布前 QC 清单、标题关键词 grep 查重。
- 排班自动化 ID：`automation-ea60dfb0-9b17-4a08-8b1f-24db73f19123`（本会话/本工作目录，每 30 分钟触发）。
- 旧 n8n 内容产线 5 个工作流（RSS 采集器/文章生成器/早报/日报/发布器）已在数据库置 `active=0` 并重启 n8n 生效——**旧产线已拆除，不是停用观察**。

### 4.3 已完成的修复
- 广告：AdSense 自动广告（锚点/插屏/页内强插）已全局停用（旧体验崩坏根源）；文章页两个受控广告位（TL;DR 后 + 文末）模板/CSS 已就位，slot ID 已配置（7719468603 / 1594607058）。
- 运维：停用拖垮 NAS 的 hugo server 常驻容器（94% CPU + 3.77GB 内存）；构建改一次性容器；deploy.py 具备构建失败拒绝推送、commit/push 失败显式报错的能力（git 锁文件事故后加固）。
- GA4 已接入并验证线上（G-VGKMBM9RCT）。
- 2026-09-10 复产当日产出：5 篇洞察 + 1 期日报 + 1 篇晚班流水洞察，全部线上验证。

### 4.4 被否决的替代方案（及否决理由——欢迎第三方挑战）
| 替代方案 | 否决理由 |
|---|---|
| 修复旧 n8n 工作流继续用 | 30 个工作流的功能/提示词/正则封在节点 JSON：不可 diff、不可测试、不可回滚；本次所有生产事故都源于此形态。拆解成本高于重建。 |
| 全部搬 GitHub Actions（内容生产云端化） | 是**终态候选**（见 §7 路线图 P1），但当天优先恢复更新 + 提示词/QC 流程未定型，先在本机跑通再迁移成本最低。尚未否决，只是延后。 |

| 保留"每条 RSS 都写全文"的旧产量 | 经济性倒挂（额度烧穿的直接原因）；已改为按选题质量门槛写。若第三方认为流量/SEO 收益大于成本，需要给出数据论证。 |
| Supabase 继续做新管线数据层 | 当前数据量（每天几十条选题+几篇文章）用文件系统 + git 即可追溯；Supabase 在国内访问不稳定（ECONNRESET 实录）。暂不引入，等需要向量去重/多端读写时再评估。 |

## 5. 收益模型（评估"更优方案"时请以此为框架）

```
广告收益 = 会话量 × 人均页数 × RPM
```
- 会话量：靠 SEO 长尾（快讯流）+ 每日更新频率（站点活性）+ 搜索收录
- 人均页数：靠内链（存量 9369 篇归档的"相关文章"尚未建设）+ 早报/日报 → 洞察正文跳转
- RPM：靠选题结构（企业级/开发者内容 CPM 高于行业八卦）、流量地域（中文站 RPM 天花板低，英文 TL;DR 试验未开始）、广告位与页面速度
- 约束：AdSense 与 Google 搜索都在惩罚低质量产内容——**质量就是流量，流量就是钱**，这条不与收益目标冲突。

## 8. 请第三方评估的核心问题（按价值排序）

1. **执行层选型**：值班自动化跑在"单人 PC 的 cron"上是否可接受？若迁移 GitHub Actions，30 分钟一次、每次可能写稿+构建+推送（构建约 4-5 分钟）的负载在免费额度（私有库 2000 分钟/月）内是否可行？动作脚本化（当前是 agent 每次现场写稿）在 Actions 上如何保真？
2. **更新频率策略**：旧系统 30 分钟一条全文（23 篇/天），新系统每 30 分钟检查、按选题门槛日产 3-10 篇。对广告收益而言，哪个频率×质量组合最优？有无数据/研究支撑？
3. **内容策略**：快讯（廉价大量）+ 精选深度（每日 1-3 篇）的双层结构 vs 旧的单层全量长文，对 SEO/AdSense 的长期影响评估。中文 AI 资讯站在 2026 年的有效流量策略是什么？
4. **告警与看门狗的最小实现**：在不增加常驻系统的前提下，"站点停更 6 小时→飞书告警"最简可靠的实现是什么？
5. **AdSense 广告位渲染 bug**：Hugo 模板注入（见 P2）为何不生效——如接受此任务，请直接给出修复。
6. **安全**：泄露 PAT 的完整处置清单是否还有遗漏（除轮换外，是否需要清理 git 历史中的 PAT 痕迹？工作流 JSON 备份里也有）。
7. **合规**：aihot.news 的使用方式（选题信号 + 原文成稿 + 署名原文链接）在"商业产品需书面授权"条款下是否站得住？
8. ** Anything missed**：任何本方案未考虑到的、对"广告收益最大化"目标有实质影响的方案或风险。
