## 2. 广告位（P2）真实根因与补丁

### 2.1 根因

Hugo 的模板查找顺序让 `layouts/page.html`（根级，50 行，2025-06-21）**通吃所有没有专属 section 模板的正文页**：

| 页面类型 | 实际渲染模板 | 判定依据 |
|---|---|---|
| 洞察 `/insights/*`（9,376 页，全站主体流量） | `layouts/page.html` | 日期 aside 位置 117 < 分享区 258 |
| 关于 `/about/` | `layouts/page.html` | 同上 |
| 日报 `/newspaper/*` | `layouts/newspaper/single.html` | 分享区 125 < 日期 aside 6629 |
| 早报 `/morningnews/*` | `layouts/morningnews/single.html` | 同日报 |
| —— | `layouts/_default/single.html`（**今天写广告的地方**） | 独有标记在全部产物中出现 **0** 次 |

本地可复现验证：把 `layouts/page.html` 移出查找范围后重新构建，洞察页立刻回落到 `layouts/_default/single.html` —— 遮蔽关系确认。

> 线上实测：`curl` 洞察页，`<ins class="adsbygoogle">` 数量 = **0**，只有 head 里的 loader 脚本。**"slot 已配置但页面 0 渲染"的直接原因就是：渲染这些页面的模板里根本没有广告代码。**

### 2.2 已验证的补丁（本地构建通过，未应用到生产）

验证结果：`ins广告位: 2 / slot_top: 7719468603 / slot_footer: 1594607058 / HTML被转义: 0 / 正文 h3: 3（内容未被破坏） / 密码残留: 0`。

**补丁 A — `layouts/partials/ads/unit.html`：删除第 1 行**

```
- ;ZqxJB`1
  {{- $slot := .slot -}}
```

**补丁 B — 把注入逻辑做成分部（partial），供 `page.html`、`newspaper/single.html`、`morningnews/single.html` 共用**。以 `layouts/page.html` 为例，把 `{{- .Content -}}` 替换为：

```go-html-template
{{- $content := .Content -}}
{{- $adTop := partials.Include "ads/unit.html" (dict "slot" site.Params.adsense.slot_after_tldr "cls" "ad-slot ad-slot-top") -}}
{{- if and $adTop (strings.Contains $content "</blockquote>") -}}
  {{- $content = replaceRE "(?s)(</blockquote>)" (printf "%s%s" "$1" $adTop) $content 1 | safe.HTML -}}
{{- end -}}
{{- $content -}}
{{- partials.Include "ads/unit.html" (dict "slot" site.Params.adsense.slot_footer "cls" "ad-slot ad-slot-footer") -}}
```

三个关键点（ZCode 原方案会踩的坑）：
1. **`safe.HTML` 必需**：`replaceRE` 返回 `string` 而非 `template.HTML`，直接输出会被 HTML 转义——正文会变成一堆可见的 `&lt;p&gt;`。实测确认加与不加差别在这里。
2. **广告要放在 `</blockquote>` 之后**，不是之前。原写法 `printf "%s%s" $adTop "$1"` 会把广告 div 塞进引用块内部（继承引用块样式）。
3. **不要只修 `_default/single.html`**。它是死文件；而且日报/早报有自己的模板，同样没有广告代码。

### 2.3 更进一步的建议：不要在这种结构上贴补丁

`page.html` / `_default/single.html` / `newspaper/single.html` / `morningnews/single.html` 是 4 份近重复的手抄副本（差异只有日期位置、侧栏 partial 名、一段注释）。**正确做法是抽一个 `layouts/partials/article-body.html`**（内容 + 广告 + tags + 相关阅读 + AI 声明），三个正文模板都只调用它。这样"广告放哪"只有一个答案，也不会再出现"改了没生效"。

## 3. 第一性原理：北极星指标反推

### 3.1 收益模型给出的唯一约束

```
广告收益 = 会话量 × 人均页数 × RPM
```

用已知数据反推（诚实标注假设）：

| 输入 | 值 | 来源 |
|---|---|---|
| 28 天收益 | $0.36 | HANDOVER §2 |
| 中文科技站 RPM（保守区间） | $0.5 – $2.0 / 千次浏览 | 行业经验值，**待 GA4 数据替换** |
| ⇒ 月浏览量 | **约 400 – 1,600 次** | 计算 |
| ⇒ 日均浏览量 | **约 13 – 53 次** | 计算 |

要达 **$100/月**：

| RPM | 所需月浏览 | 所需日浏览 | 相对当前 |
|---|---|---|---|
| $1.0 | 100,000 | ~3,300 | **~170×** |
| $2.0 | 50,000 | ~1,700 | **~85×** |

**推论（这是整份 review 最重要的一句）**：产出量从 3 篇/天提到 10 篇/天是 3.3 倍，而缺口是 85–170 倍。**继续优化生产层，无法收敛到目标。** 当前的约束在"被搜索收录"和"被外部引用"，而这两件事**今天的责任人、任务、指标都不存在**（无 GSC、无外链策略、无分发动作、无 3-7 天复盘闭环）。

### 3.2 那"质量"到底是什么

ZCode 在 §5 写"质量就是流量，流量就是钱，这条不与收益目标冲突"——但产线设计（每 30 分钟自动产出 1-3 篇基于聚合器摘要的中文改写）**本身就是"规模化生成"的定义**。两句话在同文档内互斥。

对一个小站的现实路径只有两条，且都不在"日更新闻"上：
1. **常青结构化资产**：模型/API 价格与能力的对比表、上下文成本计算器、发布时间线、术语表。搜索生命周期 12–24 个月，且**大媒体不做**——它们只做 24–72 小时的新闻。站内已具备原料：9,376 篇带日期的归档 + 旧原型留下的 `entities/` `concepts/` `timeline/` 结构痕迹。
2. **可被引用的原始整理**：比如"某模型 API 价格变更全记录"。别人的文章引你，才有外链；外链才是排名的入场券。

### 3.3 一个被忽略的合规/政策风险

Google 的 scaled content abuse 政策 + AdSense 低价值内容审查，直接指向"以第三方聚合器为信号、批量生成、无实质增量"的页面模式。**这条风险与"广告收益最大化"直接对撞**，比 §7 里任何一条 P2/P3 都更该被列为 P0/P1。

## 4. ZCode 方案的三个自相矛盾

| # | 自相矛盾 | 说明 |
|---|---|---|
| 1 | **原则 5「提示词与规范进文件」 vs `.gitignore` 排除 `newsroom/`** | `RUNBOOK.md`、`deploy.py`、`config.json` 全在 gitignore 里 → 规范不进版本控制，不可 diff、不可回滚、不可评审——这恰恰是它否决 n8n 的理由。而**进了公开仓库的却是含 SSH 密码的模板**。版本控制的边界画反了 |
| 2 | **以"封在节点 JSON 里不可 diff/测试/回滚"否决 n8n，却换成"封在 agent 会话里"** | agent 每 30 分钟现场读手册、现场 curl、现场写稿、现场决策——比 n8n 更不可复现、更不可测试、更不可回滚。**问题没解决，只是从 JSON 移到了对话里**（且更难审计：n8n 至少能导出 JSON） |
| 3 | **原则 3「失败必须可见」 vs 今天的优先级** | 37 天静默死亡的根因是"没有任何告警"。今天做的却是：停止自动广告、装广告位、接 GA4、恢复发文。P1 的看门狗仍在"候选解法"。**在会话量接近 0 时优化 RPM，等于优化一个乘以零的系数** |

补充一条：**"单一写入者"这条原则本身没错，但解法是用串行来回避冲突，而不是消除冲突。** 根因是"把 git 当内容数据库 + 构建产物分发通道"三合一：`public/` 提交了 51,940 个文件，每次发布重写上千文件 → 5 分钟构建、大 diff、锁文件事故、无意义的 `git log`。三个关注点（源 / 构建 / 分发）本该是三个系统。

## 5. 更优雅的重构方案

### 5.1 第 0 原则：把"确定性"和"判断力"分开

现状是把 agent 放在**执行器**位置（每 30 分钟现场的 cron）。更优雅的形态是把它放在**主编**位置：

| 层 | 内容 | 形态 | 频率 |
|---|---|---|---|
| L0 采集 | 拉 aihot（+直连 RSS 兜底） | 30 行 Python，纯标准库，可单测 | 每小时 |
| L1 去重 | `state/seen.jsonl`：URL 规范化 hash + 标题 3-gram 指纹 | 状态表，**取代 grep 9,376 个文件** | 同上 |
| L2 生成 | 队列 → 模板化 md（frontmatter 严格校验，失败即跳过并记录） | 一次 LLM 调用/篇，供应商可换 | 同上 |
| L3 构建发布 | `hugo --minify` → CDN | CI，**不需要 NAS、SSH、docker、paramiko** | push 触发 |
| L4 观测 | 心跳 + dead-man switch（停更 >6h 告警） | 一次 HTTP GET | 每天 4 次 |
| L5 判断力 | 选题取舍、事实核验、质量批评 | **agent，1-2 次/天，产出审阅意见而非直接发布** | 每天 |

这样 agent 从 48 次/天降到 1-2 次/天（token 消耗降约 95%），它的输出变成**可审阅的批注**而不是**不可追溯的发布动作**；同时高质量判断被用在最贵的地方（score ≥ 80 的选题核原文），而不是每篇都现场发挥。

### 5.2 分层落地（永远在线 / 有人时加料）

| 层 | 触发 | 内容 | 依赖 |
|---|---|---|---|
| **骨架层（永不停刊）** | 云端 CI 定时 | 采集 + 去重 + 早报/日报（模板化）+ 构建 + 发布 + 心跳告警 | 无需本机、无需 agent；需要一把 LLM key（或不需 LLM 的模板化） |
| **增补层（有人时加料）** | 本机 agent | 深度洞察、原文核实、质量抽检、周复盘 | ZCode 订阅，边际成本 0 |

这直接消解 P1（PC 关机=停刊）：**站点永远不会因为 PC 关机而停更**，最差情况只是当天深度稿少一点。

> 关于 §8.1 的 Actions 额度疑问：**该仓库是公开仓库，标准 runner 免费且不限时长**，"私有库 2000 分钟/月"这个前提不成立。真正的约束是：内容生成目前骑在 ZCode 订阅上（没有 API key），上云必须引入一把 LLM key，即把"边际成本 0"变成"每天几分钱"。这个取舍必须由你拍板，而不是被"额度不够"这个错误前提挡掉。

### 5.3 删除清单（比新增更重要）

| 删除项 | 理由 | 影响 |
|---|---|---|
| `newsroom/deploy.py`（71 行）+ `config.json`（SSH 密码 + PAT） | 只为"在本机旁边跑 Hugo"而存在 | 发布通道从 5 跳降到 1 跳（push） |
| `git add public/`（51,940 个文件） | 让 CI 构建产物进 CDN，不进版本库 | 仓库瘦身 ~90%，构建从 4-5 分钟变云端并行，git 冲突面消失 |
| NAS 上的 Hugo 构建链路 / `hugo server` 残留 | NAS 回归"存储 + 服务"角色 | 少一个常驻系统的运维面 |
| 仓库根目录 470+ 个旧站原型产物 + `public-test/` | 熵；已确认未被 Vercel 服务，纯粹是理解成本 | 仓库可读 |
| `layouts/_default/single.html` | 死模板，且是今天事故的现场 | 消除"改了没生效"的再次发生 |
| `static/` 里 6,420 张历史配图 | 构建慢、C 盘构建时曾把磁盘写满（实测 ENOSPC） | 迁对象存储或压缩后引用 |

**建议同时考虑：重建仓库。** `content/` 重新拉一个新仓库、单次提交，一次性解决：4,968 条 `{{ items.length }}` 垃圾 commit message（永久挂在公开历史里，是品牌负资产）、PAT 痕迹清理、51,940 文件膨胀、根目录垃圾。内容站的历史提交价值≈0，本地留一份 `git bundle` 即可。

## 6. 对 §8 八问的直接回答

| # | 问题 | 回答 |
|---|---|---|
| 1 | 值班跑在单人 PC cron 是否可接受？Actions 额度够吗？ | **不可接受**（违反自己的原则 3）。额度顾虑不成立：公开仓库不收时长费。真约束是需要一把 LLM key。保真问题用分层解决：把"写完稿"从 agent 会话搬成模板化脚本，agent 只做审阅 |
| 2 | 频率×质量哪个组合最优？ | 在会话量 ~13-53/天 时，"频率"不是自变量——**没有观测数据能支撑任何频率结论**。建议先做 1 条实验：把"每天必发早报/日报"变成"站点永不断更"的下限，把省下的产能投到常青页，2-4 周后用 GA4 的 landing page 报告判断 |
| 3 | 双层（快讯+精选）vs 单层长文？ | 双层方向对，但**缺第三层**：常青/数据层。理由是搜索生命周期差一个数量级（24-72h vs 12-24 个月）。新闻层保活性，常青层才是会话量的复利来源 |
| 4 | 看门狗最小实现？ | 不用常驻系统：CI 每 6 小时检查"最新 content 提交时间"，超阈值就发一条 webhook（飞书自定义机器人 / ServerChan / healthchecks.io dead-man switch 皆可）。**约 10 分钟工作量，零成本** |
| 5 | 广告位渲染 bug 的修复？ | 见 §2：根因是模板遮蔽；补丁 A+B 已本地构建验证通过（2 个 `<ins>`、slot 正确、无转义、内容未破坏）。**务必先删 `unit.html` 第 1 行再修**，否则密码进全站 HTML |
| 6 | PAT 处置清单是否遗漏？ | **重大遗漏**：第一，还有 NAS SSH 密码（爆炸半径比 PAT 大——NAS 是数据/服务中枢，且是 8 字符弱口令 + 密码登录 + `sudo -S` 喂密码）；第二，`ghp_` 从未 push 过？需确认；第三，**最省事的处置是重建仓库**而不是 filter-repo 挖历史；第四，`layouts/partials/ads/unit.html` 必须纳入 secret-scanning 覆盖 |
| 7 | aihot 合规站得住吗？ | **站不住的概率偏高**。RUNBOOK 自己写"事实只能来自信源摘要/原文"，而成稿事实层实际来自 aihot 的 AI 摘要（P3 也承认"未逐篇打开原文"）→ "仅作选题信号"是形式抗辩。低成本解法：把主信源换成官方 RSS/release notes（DeepSeek / OpenAI / Anthropic / Google 都有），aihot 降级为排序参考。这一条同时解决"内容同质化"问题 |
| 8 | 还有什么被漏掉的？ | 见下 §7。最实质的三条：(a) 约束在分发不在产量；(b) scaled content 政策风险与北极星对撞；(c) 9,376 篇存量是负债不是资产，需要治理（noindex/合并/补配图/归一分 类）而不是继续叠加 |
